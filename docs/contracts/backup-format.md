# Backup repository format

Status: M5a contract.

This contract fixes how Quoro stores backups in object storage: the objects of a backup repository, the keys that protect them, how a volume or the control-plane database becomes a backup, and how a backup becomes a volume or a database again. It implements ADR 0147 (repository format and keys) and ADR 0148 (control-plane backup), on top of the snapshot methods of ADR 0146 and the local volumes of ADR 0145.

The API that drives backups is in [openapi.yaml](openapi.yaml) (tags `backups` and `volumes`), the desired-state entries a node acts on are in [node-agent-protocol.md](node-agent-protocol.md) section 5.11, and the scopes are in [permission-model.md](permission-model.md). Everything below about real providers is **Hypothesis** until the storage epic has run it on the lab.

## 1. Purpose and principles

A backup has to outlive the machine it was taken on, and it has to stay unreadable to whoever holds the bucket. The principles:

1. **Data goes from the node to the bucket.** The node that holds a volume reads its snapshot and uploads it directly. App data never passes through the primary (ADR 0014, ADR 0147).
2. **Encrypted before it leaves.** Every chunk and every manifest is compressed and encrypted on the machine that writes it. The bucket only ever holds ciphertext, ids, sizes and times.
3. **Readable without the primary.** The repository key is wrapped twice: under the cluster data-encryption key for unattended backups, and under a recovery key that only the owner holds. A lost primary does not take the backups with it, as long as the owner kept the recovery key and the cluster key files (section 8.2).
4. **Only the primary seals.** A backup counts only once the primary has written its seal, signed with the cluster signing key. A node never holds that key, so a node, or anyone else with bucket access, cannot make a backup look valid.
5. **Write once.** Every object is written with `If-None-Match: *`. Quoro never overwrites an object; it deletes only through retention and garbage collection on the primary (section 9).
6. **Nothing is mounted on the host.** Backups read a volume file as bytes, and restores write bytes. The host never mounts a filesystem a guest has written (ADR 0145).

## 2. Layout

A repository lives under a key prefix in the bucket of one `object_store` provider (`backup_repositories.provider_id` and `prefix`). Every key below is relative to `<prefix>/<cluster_id>/`:

| Key | Written by | Content |
| --- | --- | --- |
| `config-<n>.json` | primary | Repository config, with the repository key wrapped under the recovery key (section 4). `n` is a decimal counter from 1, without padding. |
| `chunks/<first 2 hex of id>/<id>` | the node or primary that took the backup | One encrypted chunk (section 5). `id` is 64 lowercase hex. |
| `manifests/<source_id>/<backup_id>` | the node or primary that took the backup | One encrypted manifest (section 6.1). |
| `seals/<source_id>/<backup_id>.json` | primary | The signed seal of a succeeded backup (section 6.2). |

`source_id` names the source of the backup and is stable for its whole life:

- for a volume backup, the **app id**, not the volume id. A restore creates a new volume for the same app, and the next backup of that app still deduplicates against the earlier ones;
- for a control-plane backup, the **cluster id**.

The off-site audit copy uses another provider entry and another prefix (audit-log-format.md section 8). The two never share a credential (section 10).

## 3. Keys

All keys are 256 bits. Derivations use BLAKE3 in key-derivation mode, `derive_key(context, material)`, with the context strings below, which are fixed for format version 1.

| Key | Derivation | Who holds it |
| --- | --- | --- |
| `repo_key` | 32 random bytes, generated by the primary when the repository is created | Primary, wrapped under the cluster DEK in `backup_repositories.repo_key_enc`, which never enters the change log; in the bucket, wrapped under the recovery key (section 4) |
| `source_key` | `derive_key("quoro backup source v1", repo_key ‖ source_id)`, with `source_id` as its ASCII bytes | Never stored; derived when needed |
| `id_key` | `derive_key("quoro backup chunk id v1", source_key)` | Primary; a node, for the one source of its current job |
| `data_key` | `derive_key("quoro backup chunk data v1", source_key)` | Primary; a node, for the one source of its current job |
| `wrap_key` | `derive_key("quoro backup recovery wrap v1", recovery_key)` | Never stored; derived from the recovery key when it is generated or typed in |

What follows from the table:

- **A node only reads the source it backs up or restores.** A job carries the `id_key` and `data_key` of that source, never `repo_key` (node-agent-protocol.md section 5.11). A compromised node can read the backups of the apps it was given jobs for, which it already holds the live data of, and no others.
- **Dedup is per source.** Two apps with identical data store it twice. This is the price of per-source keys. Within one app, every backup after the first uploads only the chunks that changed.
- **The recovery key** is 32 random bytes generated by the primary when the repository is created and each time it is replaced (`rotateBackupRecoveryKey`). It is shown to the owner once, in the response of that call, and never stored in plaintext anywhere. Its text form is `qrk1-` followed by the 256-bit value as a big-endian number in Crockford base32 (alphabet `0-9 A-H J K M N P-T V-Z`), 52 characters with the four leading padding bits zero, in 13 groups of 4 separated by `-`. A form with nonzero padding bits is rejected. Input ignores case and treats `O` as `0` and `I` or `L` as `1`.
- **The recovery key fingerprint** is the first 16 hex characters of `derive_key("quoro backup recovery fingerprint v1", recovery_key)`. It is stored in `backup_repositories.recovery_key_fingerprint` and in the config object, and it is shown in the API, so an owner can check which key they hold without revealing it.

## 4. Config object

The primary writes `config-<n>.json` when it creates the repository (`n = 1`) and each time the recovery key is replaced (`n + 1`). It is plain JSON:

```json
{
  "format": 1,
  "repository_id": "brp_01JCA0A2B3C4D5E6F7G8H9J0KM",
  "cluster_id": "cls_01JC9Z1A2B3C4D5E6F7G8H9J0K",
  "cluster_public_key": "u3VbJk9rQ0Lw8m1Wq2zT5yHc6nE4aP7sDf0gXiK2oVQ=",
  "recovery_key_fingerprint": "4f1c9a07b2d8e6a3",
  "wrapped_repo_key": {
    "alg": "xchacha20poly1305",
    "nonce": "base64 of 24 bytes",
    "ciphertext": "base64 of the 32-byte repo_key and the 16-byte tag"
  },
  "created_at": "2026-11-05T02:00:00Z"
}
```

- `wrapped_repo_key` is `repo_key` encrypted under `wrap_key` with a random nonce. The associated data is the ASCII bytes of `repository_id`.
- `cluster_public_key` is the base64 public half of the cluster signing key, so the reader knows which key the seals must verify against. It is only a hint: an offline restore checks it against the signing key file the operator supplies (section 8.2).
- **Rotation.** After it writes `config-<n+1>.json`, the primary deletes every `config-<m>.json` with `m ≤ n`, so the old recovery key no longer opens the repository. A reader uses the config object with the highest `n` that the given recovery key opens. A config object planted by someone else cannot hold the real `repo_key`, because writing one needs `repo_key` in the first place.
- **Restoring the key on a primary (ADR 0322).** A primary that does not hold `repo_key`, as after a promotion (node-agent-protocol.md section 7.3), gets it back with `restoreBackupRepositoryKey`, which takes the recovery key. The primary:
  1. checks that the recovery key's fingerprint equals `backup_repositories.recovery_key_fingerprint`, before it reads the bucket;
  2. lists the config objects and unwraps `repo_key` from the newest one the recovery key opens, as `quoro restore` does (section 8.2);
  3. stores `repo_key` wrapped under the cluster data-encryption key in `repo_key_enc`, on this primary only. The write appends no change-log entry, so no follower and no later primary receives the key.

  The recovery key is held only for the call and is redacted from its audit record (`audit-log-format.md` section 4). A primary that already holds `repo_key` answers `conflict`.

## 5. Chunks

- **Chunking.** FastCDC, the 2020 variant, with a minimum of 256 KiB, an average of 1 MiB and a maximum of 4 MiB, over the whole snapshot file. Each backup scans the full snapshot (ADR 0146). There is no change tracking between backups.
- **Chunk id.** `BLAKE3-keyed(id_key, plaintext)`, as 64 lowercase hex. A plain content hash would let anyone who can read the bucket test whether a known file is in a backup; a keyed id does not.
- **Chunk object.** The plaintext compressed with zstd at level 3, then encrypted with XChaCha20-Poly1305 under `data_key`, with a random 24-byte nonce and the chunk id's ASCII bytes as associated data. The object is `nonce ‖ ciphertext ‖ tag`.
- **Upload.** `PUT` with `If-None-Match: *`. A `412` means the chunk is already in the repository and counts as a success. A node may keep a local list of chunk ids it knows the repository holds and skip those uploads; the list is a hint, and a wrong entry is caught at restore (section 8.1).
- **All-zero chunks** are uploaded like any other chunk. They deduplicate to a few objects, and a restore writes them back as holes in the sparse file.

## 6. Manifest and seal

### 6.1 Manifest

The machine that took the backup writes one manifest per backup, after its last chunk is acknowledged. The plaintext is JSON:

```json
{
  "format": 1,
  "backup_id": "bkp_01JCA1A2B3C4D5E6F7G8H9J0KM",
  "cluster_id": "cls_01JC9Z1A2B3C4D5E6F7G8H9J0K",
  "repository_id": "brp_01JCA0A2B3C4D5E6F7G8H9J0KM",
  "source_kind": "volume",
  "source_id": "app_01JC9Z7B3N5Q7S9Z1W3Y5A7C9E",
  "volume_id": "vol_01JC9ZC2D3E4F5G6H7J8K9M0NP",
  "fencing_token": 3,
  "snapshot_method": "reflink",
  "logical_bytes": 10737418240,
  "chunker": { "algorithm": "fastcdc2020", "min": 262144, "avg": 1048576, "max": 4194304 },
  "chunks": [
    { "id": "9c4e…", "offset": 0, "length": 1048576 },
    { "id": "51a0…", "offset": 1048576, "length": 731402 }
  ],
  "quoro_version": "0.6.0",
  "created_at": "2026-11-05T03:00:41Z"
}
```

- For a control-plane backup, `source_kind` is `control_plane`, `source_id` is the cluster id, and `volume_id`, `fencing_token` and `snapshot_method` are absent.
- The chunks are listed in file order, with no gaps and no overlaps, and their lengths add up to `logical_bytes`.
- The object is the JSON compressed with zstd and encrypted like a chunk under `data_key`. Its associated data is the ASCII bytes of `manifest:` followed by `backup_id`, so a manifest cannot be passed off as another backup's.
- `manifest_digest` is the BLAKE3 hash (unkeyed) of the encrypted object's bytes, as 64 lowercase hex. The node reports it to the primary with the manifest's key (node-agent-protocol.md section 5.3).

### 6.2 Seal

The primary writes the seal, and the backup becomes `succeeded`, only after it has checked three things: that the manifest object exists, that its digest matches the reported one, and, for a volume backup, that the backup's `fencing_token` still equals the token of the app's current `local` lease. If the lease moved while the backup ran, the backup fails with `lease_moved` and gets no seal. The seal is plain JSON:

```json
{
  "format": 1,
  "backup_id": "bkp_01JCA1A2B3C4D5E6F7G8H9J0KM",
  "cluster_id": "cls_01JC9Z1A2B3C4D5E6F7G8H9J0K",
  "repository_id": "brp_01JCA0A2B3C4D5E6F7G8H9J0KM",
  "source_kind": "volume",
  "source_id": "app_01JC9Z7B3N5Q7S9Z1W3Y5A7C9E",
  "volume_id": "vol_01JC9ZC2D3E4F5G6H7J8K9M0NP",
  "fencing_token": 3,
  "manifest_key": "manifests/app_01JC9Z7B3N5Q7S9Z1W3Y5A7C9E/bkp_01JCA1A2B3C4D5E6F7G8H9J0KM",
  "manifest_digest": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "logical_bytes": 10737418240,
  "chunk_count": 10240,
  "created_at": "2026-11-05T03:00:00Z",
  "sealed_at": "2026-11-05T03:00:42Z",
  "signature": "base64 Ed25519 signature"
}
```

- `signature` is the Ed25519 signature, by the cluster signing key, over the RFC 8785 canonical JSON of the object without `signature`.
- A seal holds ids, sizes and times, never data. Anyone who can read the bucket can see which apps have backups, how large they are and when they ran. This is accepted for M5a.
- A backup without a seal does not exist for a restore. Its manifest and chunks are removed by garbage collection (section 9).

## 7. Taking a backup

### 7.1 A volume

1. The primary records the backup as `queued`, with the token of the app's current `local` lease. It adds a job to the `spec.backups[]` of the volume's node, carrying `id_key` and `data_key` for the app, and the repository's endpoint and credential in `spec.backup_repository` (node-agent-protocol.md section 5.11). One backup per volume runs at a time. The primary does not dispatch a backup while a garbage-collection sweep of the repository runs (section 9).
2. The node checks the job's `fencing_token` against the lease it holds for the app. If they differ, it reports the backup `failed` with `lease_mismatch` and does nothing else.
3. The node takes the snapshot with its method (engine-trait.md section 3.16). From M5b the engine first asks the guest to flush the volume's filesystem (ADR 0282). Then `reflink` clones the file without stopping the app, and `pause_copy` pauses the VM, copies the sparse file and resumes it. The node reports `running` together with `snapshot_method`, `pause_ms` for `pause_copy`, and from M5b `guest_flush` (node-agent-protocol.md section 5.3). A `false` `guest_flush` does not fail the backup. The manifest does not record it.
4. The node chunks the snapshot, uploads the chunks (section 5), writes the manifest (section 6.1) and deletes the snapshot file. It then reports the backup with `manifest_key`, `manifest_digest`, `logical_bytes`, `uploaded_bytes` and `chunk_count`. Any error is reported as `failed` with a one-line reason, and the snapshot file is deleted.
5. The primary seals the backup (section 6.2), records it `succeeded` and emits `backup.succeeded`, or records it `failed` and emits `backup.failed`. Either way it removes the job from desired state.

A backup not terminal 24 hours after it was dispatched is recorded `failed` with `timeout`. Schedules (`App.backup_schedule`, while `ha_policy` is `cold`) count from the last succeeded backup of the source. A failed scheduled backup is retried at the next interval, not sooner.

### 7.2 The control-plane database

The primary runs `VACUUM INTO` to a temporary file in its data directory, outside any open transaction (ADR 0148). It then feeds that file through the same steps 4 and 5 itself, with the cluster id as `source_id`, and deletes the temporary file. It runs on the repository's `control_plane_schedule` (default every 6 hours, keep 7) and before an upgrade. If the seal cannot be written, the backup is recorded `failed` at once, as in section 7.1. The cluster key files are not part of the database and not part of the backup (section 8.2).

**Before an upgrade (ADR 0157).** Installing a new version replaces the binary without asking the running primary, so the new binary takes the backup itself, at its first start and before it applies any migration. No API operation starts it.

1. The primary reads the database's `schema_version` and compares it with the newest version the binary ships. When none are pending, or when the database is new, it starts as usual.
2. When migrations are pending and a repository is configured, it runs `VACUUM INTO`, uploads the chunks, writes the manifest and writes the seal, as above, all before it changes the database. The backup has `trigger: upgrade`. With no repository configured, which includes a database too old to have the `backup_repositories` table, there is nothing to write to, so the primary logs that it migrates without a backup, and migrates. This read runs against the old schema, so a later migration must keep the repository columns it uses readable, or the primary treats the repository as absent. A repository whose key this primary does not hold, after a promotion (node-agent-protocol.md section 7.3, step 4), fails the backup, so step 4 applies.
3. Only after the seal is written does it apply the migrations. It then records the backup `succeeded` in the migrated database, with its change-log entry and its `backup.dispatch` and `backup.seal` audit records, and runs retention for upgrade backups (below).
4. If any step of the backup fails, the primary applies no migration, leaves the database as it was, and exits non-zero with a one-line reason. A later start tries the backup again. To migrate without the backup, the operator stops the service and starts the binary once with `quoro serve --skip-upgrade-backup`. The primary then migrates, writes a `backup.upgrade_skipped` audit record (audit-log-format.md section 3.5), and runs as usual. A start with that flag and nothing pending, or with no repository, skips nothing and writes no record.

A crash after the seal is written and before the row is recorded leaves a sealed backup that the database does not list. `quoro restore` still finds it, because it reads the seals (section 8.2), and garbage collection keeps its chunks, because it is sealed (section 9). Retention counts recorded backups only, so it leaves that one in place.

**Rows left behind at start.** The primary takes a control-plane backup inside its own process, so a control-plane backup that is `queued` or `running` when the primary starts was interrupted: the primary stopped or crashed during it, or the database was restored from that very backup, whose row `VACUUM INTO` copied while it was `running` (section 8.2). Before its backup loop starts, the primary resolves each such row:

- when `seals/<cluster_id>/<backup_id>.json` exists, verifies with the cluster signing key (section 6.2) and names this backup, its repository and the cluster, the primary records the backup `succeeded` from the seal: `manifest_key`, `manifest_digest`, `logical_bytes` and `chunk_count` come from the seal, `finished_at` is its `sealed_at`, and `uploaded_bytes` stays null. The change-log entry, the `backup.seal` audit record and the `backup.succeeded` event are the ones of a sealed backup; the event's required `uploaded_bytes` is 0, because the seal does not carry it;
- when that object does not exist, the primary records the backup `failed` with the reason `interrupted`;
- when that object exists but does not verify or names another backup, repository or cluster, the primary records the backup `failed` with the reason `the seal does not verify`;
- when the bucket cannot be read, the row stays as it is, and the 24-hour timeout of section 7.1 still applies.

A row resolved this way no longer blocks the schedule, which counts from it like from any other finished control-plane backup. Resolving a row runs no retention (section 9): at start the database may be older than the bucket, so the next control-plane backup that succeeds prunes as usual.

**Retention of upgrade backups (ADR 0158).** `control_plane_schedule.keep` counts only control-plane backups with `trigger: schedule`, and their pruning never removes an upgrade backup. Backups with `trigger: upgrade` are counted on their own: after one succeeds, the primary prunes the oldest succeeded, unpruned upgrade backups beyond 3, the same way as in section 9. Garbage collection never removes a chunk that a kept upgrade backup references; since a kept backup is sealed, the sweep of section 9 already treats its chunks as live.

## 8. Restoring

### 8.1 A volume, through the API

`restoreBackup` (openapi.yaml) creates a new volume in `restoring` on the target node. That volume's entry in `spec.volumes[]` carries a `restore` object with the backup id, the manifest key, the manifest digest from the seal record, and the source's `id_key` and `data_key`. The target node:

1. reads the manifest, checks its BLAKE3 digest against the one it was given, decrypts it, and checks that `backup_id` and `source_id` match the job;
2. creates a sparse file of the volume's size, then for each chunk: reads it, decrypts it with the chunk id as associated data, decompresses it, checks that `BLAKE3-keyed(id_key, plaintext)` equals the id, and writes it at its offset. An all-zero chunk is left as a hole;
3. checks that the chunks covered `logical_bytes` exactly, and reports the volume `ready`.

Any failed check stops the restore: the node deletes the partial file and reports the volume `failed` with the reason. The primary then emits `restore.failed`. Nothing on the target node is mounted at any point.

### 8.2 The control-plane database, offline

A control-plane backup is restored on a fresh host with the CLI (`quoro restore`, ADR 0148), not through the API. It needs four inputs:

| Input | Why |
| --- | --- |
| The bucket's endpoint, region, bucket name, repository prefix and cluster id, plus a credential that may get and list | To read the repository |
| The recovery key | To unwrap `repo_key` from the config object |
| The cluster signing key file | To verify the seals, and so that the nodes, which pinned its public half at enrollment, accept the restored primary's desired state |
| The cluster data-encryption key file | To read every `*_enc` column of the restored database: provider secrets, environment values, node credentials and `repo_key_enc` itself |

The key files live in `/var/lib/quoro`, outside the database, and are backed up separately ([architecture.md](../architecture/architecture.md) section 6, "Cluster keys"). **They are not in the repository.** Without the signing key file, the restored primary cannot sign desired state that any enrolled node accepts. Without the data-encryption key file, every secret in the restored database is unreadable. In both cases `quoro restore` refuses to proceed, rather than install a primary that cannot work.

The restore:

1. lists the config objects and unwraps `repo_key` from the newest one the recovery key opens;
2. checks that the config's `cluster_public_key` equals the public half of the given signing key;
3. lists `seals/<cluster_id>/`, verifies each seal's signature with the given signing key, and picks the newest valid one, or the one the operator named;
4. reads and checks the manifest and the chunks as in section 8.1, writing the database file;
5. runs SQLite's `PRAGMA integrity_check` on the file, and only then installs it with the key files into the new host's data directory.
6. names the node on the new host that takes the primary status (below), by writing its `nod_` id to `primary-node` in the data directory, mode 0600.

**The primary status moves with the restore.** `nodes.cp_status = 'primary'` names the node on the primary's host (`getCluster.primary_node_id`, `welcome.primary_node_id`, and the `node_id` of control-plane backups). Only the local enrollment of the primary's own agent sets it, whatever that agent's roles, so a restore onto another host would leave it on the old host's node. While no machine holds it, as in a new cluster before the primary's own agent enrolls, after an `--accept-loss` first write that leaves the new host's node without it until that agent enrolls ("The first write" below), and for good on a host whose agent never enrolls locally (one that runs no node agent): `Cluster.primary_node_id` is null; `welcome.primary_node_id`, and the `support_request`s of that session, name the connecting machine's own id, so a support a voter stores then names that voter, which node-agent-protocol.md section 8.9 rule 2 never counts for that voter's own candidacy: the voter waits out that promise before it votes for itself (sections 8.8 and 8.9 there); and a control-plane backup, the pre-upgrade backup of section 7.2 included, goes on with a null `node_id`, which `backup.succeeded` and `backup.failed` leave out (events.schema.json). `quoro restore` therefore picks the new host's node: the node named by `--node-id NOD`, otherwise the one in this host's node agent identity file (`/var/lib/quoro-node/identity.json`), when that file exists.

- An explicit `--node-id` that the restored database does not hold, or holds as `removed`, refuses the restore before anything is installed.
- An identity file that names another cluster, or a node the restored database does not hold or holds as `removed`, writes no `primary-node` file; the restore says why and goes on. Without `--node-id` and without an identity file, no file is written either. In these cases the primary status stays where the backup had it, except after `--accept-loss`, whose first write clears it on every machine (below).

At its next start, before it serves, the primary reads `primary-node`. When the file names a node of the database that is not `removed` and does not already hold the status, the primary clears `cp_status` on the node that holds it and sets `cp_status = 'primary'` on the named node, in one change-log write, and records `cluster.primary_moved` (`audit-log-format.md` section 3.5). From M5b that write is the restored primary's first write (below), so the two are one write (ADR 0280). In every case it then deletes the file; a node it cannot use is logged with the reason. The file must have the same owner as the database file, so that the control plane can read and delete it.

**When a restore is refused (from M5b, ADR 0261).** A restored log may lack writes that every node already holds, such as the write that ends an `expiring` lease's renewals (node-agent-protocol.md section 8.4), and the restored primary would reuse that log's term and `seq` values. So `quoro restore` refuses, before anything is installed, when a machine with the `node` role other than the new host's node, and not `removed`, appears in either of two sources:

- the restored database;
- the newest `spec.votes.voters` stored by the new host's node agent, which covers nodes enrolled after the backup.

Such a cluster recovers by promoting a surviving node (node-agent-protocol.md section 7.3), which keeps every entry its nodes all acknowledged. A cluster whose only node is the new host's own restores as before. The refusal can miss a node enrolled after the backup if the host's agent never learned of it.

**Override.** `quoro restore --accept-loss --statement <text>` restores anyway. The statement says that no other machine with the `node` role survives, and that no control plane of this cluster runs. The first part also rules out a concurrent promotion, because only such a machine can be a candidate. The second rules out an old primary on a host without the `node` role that keeps granting. A single-node cluster restored onto a fresh host needs the flag too, because the dead node is not the new host's node.

**The first write.** The restored primary's first change-log write, at its first start and before it serves, marks every `expiring` lease row unsettled (`leases.unsettled`, node-agent-protocol.md section 8.4, "The mark"), after any restore. When `primary-node` asks for it, the same write also moves the primary status and records `cluster.primary_moved` (above, ADR 0280). After a restore with `--accept-loss`, the same write also:

- removes every machine with the `node` role that the statement declares gone, that is, every one in the restored database that is not `removed`, other than the new host's node, and clears `cp_status` on each, so no removed machine holds the primary status. When the new host's node holds the status after the write, because it held it already or the write moved it (above), nothing more follows; when the write moved it, `cluster.primary_moved` names as `from_node_id` the machine that held the status when the write began, one the write removes included. Otherwise (no `primary-node` file is present, or it names a node the primary cannot use), the write clears `cp_status` on every machine that holds it, whatever its roles, so an old primary on an edge-only or witness-only machine (ADR 0261) holds it no longer either: the operator's statement says that no control plane of this cluster runs. That clear records no `cluster.primary_moved`; `cluster.restored` stands for it (`audit-log-format.md` section 3.9). No machine then holds the status until the next local enrollment of the new host's agent takes it, whatever that agent's roles, and for good on a host whose agent never enrolls locally; meanwhile the fields read as "The primary status moves with the restore" says (above);
- raises the token of every lease row that names those machines, revoked rows included except one already revoked at 2^53 - 1, as declaring a node lost does (node-agent-protocol.md section 8.3), also for a machine the restored database already records declared lost; the write sets no `lost_at`. An unrevoked row at the cap refuses the restore, and stops a first start that finds one ("Override" above and "Detecting the first start" below);
- deletes their custody seals (node-agent-protocol.md section 7.2);
- records `cluster.restored` (`audit-log-format.md` section 3.9).

That write may remove more than one voter at once, so it is exempt from node-agent-protocol.md section 8.10 rules 1 and 2 (ADR 0280). Without it the dead nodes would count in every majority, so the restored primary would never hold support and could neither remove nor enroll a node. What is left after it: the restored primary needs a majority of the remaining voters, as any primary does. A new host without the `node` role leaves a cluster with no node.

**Detecting the first start (ADR 0285).** From M5b, `quoro restore` also writes a marker file, `restore-pending`, next to the database and to `primary-node`, with the same owner as `primary-node`. It writes the marker before it installs the database in step 5, so no restored database is installed without it. The marker names the database it belongs to: it holds the restored log's head `seq` and that entry's hash. It also holds whether `--accept-loss` was given and, if so, the operator's statement. When `quoro restore` stops before it installs the database, it deletes the marker.

At each start, the primary looks for the marker and deletes it before it serves:

- **The marker matches `meta.restore_marker`:** the first write above already committed. The primary deletes the marker without writing again.
- **The marker matches the installed database's log head:** this is the first start after a restore. The primary makes the first write above from it, taking `--accept-loss` and the statement from the marker. The first write is one transaction, and it also records the marker's head `seq` and hash in `meta`, under the key `restore_marker`. `meta` is not in the log (node-agent-protocol.md section 7.3 step 4), so this is a local record. The primary deletes the marker once that transaction commits.
- **Otherwise:** the marker belongs to another database. The primary logs it and deletes it, and makes no first write from it.

A crash before the first write commits leaves nothing written, and the next start makes the write. A crash after the commit and before the deletion leaves a marker that matches `meta.restore_marker`, so the next start deletes it without writing again. The first write therefore runs once per restore: no second `cluster.restored` is recorded, and no node enrolled after the restore is removed.

While a `restore-pending` marker exists on the host, `quoro cluster promote` refuses (node-agent-protocol.md section 7.3). The operator finishes the restore, or deletes the marker after checking that no `quoro restore` runs on the host.

**Term.** The restored primary starts one above the highest of: the restored log's terms; the term its host's node agent stored; and the terms in any vote `check` answers it receives (a `check` changes nothing, node-agent-protocol.md section 8.9). A fresh host is no mesh peer and may reach no voter, so an `error` with code `stale_term` carries the sender's term (node-agent-protocol.md section 5.18). A primary restored with `--accept-loss` that receives one before it has sent any `lease_grant` starts again at one above that term, instead of demoting itself (node-agent-protocol.md section 8.8). A voter that voted in the restored primary's own term for another candidate answers its `support_request` with `bad_message` instead, which carries the voter's `term` (node-agent-protocol.md section 5.27, ADR 0280). A primary restored with `--accept-loss` that has sent no `lease_grant` yet treats it like `stale_term`, and starts again at one above that term. A plain restore lacks that voter's support. The way out is to restore again, which starts above the term the voters then report, or to remove that voter's vote, with `force` when node-agent-protocol.md section 8.10 asks for it. No term the restored primary takes passes the term ceiling, 2^53 - 1 (node-agent-protocol.md section 8.8). A restored primary whose first term would pass it writes nothing, and a primary restored with `--accept-loss` whose restart at one above an error's `term` would pass it demotes itself instead. Both are stated limits.

**Tokens after a forced recovery.** A token issued in entries the restored log lacks may be issued again to another node, as node-agent-protocol.md section 7.3 says for `--ack-fence`.

The restored database is as old as the backup. It lists the backup it was restored from as `running`, which the restored primary resolves at its first start (section 7.2, rows left behind at start). How a restored primary reconciles with nodes that applied newer desired state is part of the storage epic; it does not change this format.

## 9. Retention and garbage collection

- **Pruning.** After a backup of a source succeeds, the primary prunes the oldest succeeded, unpruned backups of that source beyond its `keep` count. For the control-plane database, `keep` counts only scheduled backups; upgrade backups keep 3 (section 7.2, ADR 0158). To prune a backup, it deletes the seal first, then the manifest, and then sets `pruned_at`. The backup record stays. Failed backups count toward nothing and are never pruned.
- **Deleted apps.** In M5a nothing prunes the backups of an app that was deleted. They stay in the repository and in the backup list, and no operation restores or deletes them. Removing them is later work.
- **Garbage collection.** A mark-and-sweep on the primary removes chunks that no sealed backup references. It runs at most once a day, after a pruning. While it runs, the primary dispatches no backup of that repository, and it does not start while a backup of that repository is `queued` or `running`. A chunk that an in-flight backup found already present (`412`) therefore cannot disappear under it. The sweep:
  1. lists the seals, and reads and decrypts their manifests, which the primary can do for every source because it holds `repo_key`; the chunk ids those manifests list are live. A primary that does not hold `repo_key`, after a promotion, does not start the sweep (node-agent-protocol.md section 7.3, step 4);
  2. deletes every manifest that has no seal and was written more than 48 hours ago;
  3. lists the chunks, and deletes every chunk that is not live and was written more than 48 hours ago.
- The 48-hour grace exceeds the 24-hour backup timeout, so a sweep that starts right after a slow backup failed still leaves alone what that backup wrote. An object listing that fails part way stops the sweep without deleting anything.

## 10. Credentials

- An `object_store` provider entry names `endpoint` (an `https://` URL), `bucket`, `access_key_id` and optionally `region` (`auto` when absent) in its `config`; its secret is the secret access key. Requests are signed with AWS Signature Version 4.
- The repository's provider entry needs get, put, list and delete on its prefix, because pruning and garbage collection delete. It is a different provider entry from the audit export's, whose credential may not delete (audit-log-format.md section 8). `createBackupRepository` and `createAuditExport` refuse to share one (openapi.yaml).
- The primary sends the credential to a node only in the signed desired state, in `spec.backup_repository`, and only while that node has a backup job or a restore. The node stores it encrypted with its node-local key, as it stores tunnel tokens, and deletes it when the field disappears (node-agent-protocol.md section 5.11).
- A node uses the credential only for `PUT` and `GET` of chunk and manifest objects. Listing, pruning and garbage collection run on the primary.

## 11. What this contract does not fix

- **Provider behaviour** beyond `PUT` with `If-None-Match: *`, `GET`, `LIST` and `DELETE` is out of scope. Multipart upload is not used: the largest object is a 4 MiB chunk plus its overhead.
- **Cross-source dedup**, incremental snapshots and change tracking are not part of format version 1.
- **Restoring onto another cluster** (a different cluster id) is not supported in M5a.
- **Format changes** bump `format` in the config object, the manifests and the seals. A reader refuses a format it does not know.
