# Release artifacts

Quoro ships one tarball per release with two static binaries, built from the
tag inside the release build image (`packaging/container/Containerfile`, ADR
0090) with the Rust toolchain pinned in `rust-toolchain.toml` and the Node.js
pinned in `packaging/node.txt`. The web panel is compiled into the `quoro`
binary by `rust-embed`, so the panel's bytes are release bytes too. The release
is signed with GitHub artifact attestations (Sigstore, SLSA build provenance)
and the build is byte-for-byte reproducible on any x86_64 Linux host with
podman or docker (ADR 0027). A tag push creates a **draft** release; the
maintainer publishes it. Publishing the release also builds the documentation
site from the release tag and deploys it to GitHub Pages at quoro.dev
(`.github/workflows/docs-site.yml`, ADR 0130).

## Artifact layout

For a tag `v0.1.0` (the version is the tag without the leading `v`):

```
dist/quoro-0.1.0-x86_64-unknown-linux-musl.tar.gz
dist/quoro-0.1.0-x86_64-unknown-linux-musl.tar.gz.sigstore.jsonl
dist/SHA256SUMS
```

The tarball holds exactly one top-level directory:

```
quoro-0.1.0-x86_64-unknown-linux-musl/
├── quoro               0755  static x86_64-musl binary; the web panel is embedded
├── quoro-init          0755  static x86_64-musl binary; PID 1 inside every microVM
├── LICENSE             0644  AGPL-3.0-only, copied from the repository root
├── quoro.service       0644  systemd unit, from packaging/systemd/quoro.service
├── quoro-node.service  0644  systemd unit, from packaging/systemd/quoro-node.service
├── pins.txt            0644  engine pins, copied from crates/engine/pins.txt
└── ingress-pins.txt    0644  tunnel connector pins, copied from crates/ingress/pins.txt
```

`quoro.service` is the control plane and `quoro-node.service` the node agent:
the installer enables the first on a primary and the second on both roles (ADR
0089).

`pins.txt` is the engine's list of pinned Cloud Hypervisor and guest-kernel
artifacts. `install.sh` reads it, downloads those artifacts and verifies each
against the sha256 in the file, so the release pins the hypervisor it was tested
with instead of resolving "latest" at install time.

`ingress-pins.txt` is the same shape (name version arch file url sha256) for the
`cloudflared` connector the node agent runs to serve app hostnames through
Cloudflare Tunnel (ADR 0024, ADR 0055), one line per architecture. `install.sh`
stages it as `/usr/local/lib/quoro/cloudflared` only when the sha256 matches, so
a tunnel binary is never run that the attested tarball did not pin. It is a
separate file from `pins.txt` because the two are consumed by different parts of
the host and bump on their own schedules.

`SHA256SUMS` is `sha256sum` format and covers the tarball only. The
`.sigstore.jsonl` bundle is the offline copy of the attestation; it is
generated by the release workflow, so it exists only for workflow builds.

## Software bill of materials (from M5a)

From the M5a release on, every release also carries a CycloneDX SBOM of
what it ships, so Quoro and its operators can tell which known
vulnerabilities affect it (ADR 0138, ADR 0150):

```
dist/quoro-<version>-x86_64-unknown-linux-musl.cdx.json
dist/quoro-<version>-x86_64-unknown-linux-musl.cdx.json.sigstore.jsonl
```

- **Format.** CycloneDX 1.6, JSON. The metadata component is the release
  itself (`quoro`, the version, the tarball's sha256). Each component carries
  a package URL and, where the source states one, its license.
- **Contents.** Every crate compiled into `quoro` and `quoro-init`, from the
  `Cargo.lock` of the tag with the target's features; the npm packages
  bundled into the embedded web panel, from its lockfile; and the pinned
  artifacts the release installs or runs, with their sha256: each line of
  `pins.txt` (Cloud Hypervisor, the guest kernel), of `ingress-pins.txt`
  (`cloudflared`) and the BuildKit image the node agent pins for builds.
  Nothing else: the host's packages are the operator's.
- **Built and signed like the tarball.** It is produced inside the release
  build image from the same tag, so `reproduce-release.sh` rebuilds it
  byte for byte; its serialization is sorted and has no timestamp other than
  the tag's commit time. The release workflow attests it with the same
  Sigstore provenance as the tarball (ADR 0081), and `SHA256SUMS` gains its
  line.
- **Embedded.** The same component list is compiled into `quoro`, so a
  running primary knows what it is made of without the file. It matches that
  list against its vulnerability data every day and shows "this Quoro has
  known vulnerabilities" with the release that fixes them
  (`GET /api/v1/vulnerabilities`, `docs/contracts/openapi.yaml`).
- **RustSec stays in CI.** `cargo-deny` keeps checking the RustSec advisory
  database on every pull request; the SBOM is what lets an installed release be
  checked after it shipped.

## How the build is made reproducible

The build runs in a container, and `packaging/build-release.sh` pins every
input that can reach the bytes inside it.

### The release build image

C code reaches the `quoro` binary through its dependencies (ring and aws-lc
through rustls, the bundled SQLite), and it is compiled by the C compiler of
the build host. A build on Debian with GCC 14 and one on Ubuntu with GCC 13
produced different binaries from the same commit. So the release workflow and
`packaging/reproduce-release.sh` both run the build in one image, built from
`packaging/container/Containerfile` by `packaging/build-in-container.sh`:

| Input | Pinned by |
| --- | --- |
| Base system | `ubuntu:24.04` by its linux/amd64 manifest digest |
| C compiler, binutils, musl, git, curl, python3, xz | apt from `snapshot.ubuntu.com` at one fixed timestamp, every package installed by name at an exact version; the snapshot fixes the rest of the dependency closure |
| rustup | `rustup-init` by version and sha256 |
| Rust toolchain, components and the musl target | `rust-toolchain.toml`, installed into the image |
| Node.js | `packaging/node.txt`, sha256-verified by `packaging/fetch-node.sh`, installed into the image |

`packaging/build-in-container.sh [VERSION]` builds the image (tagged
`quoro-release-build:<hash of its inputs>`, kept for the next run) from a
context that holds only the Containerfile, `rust-toolchain.toml`,
`packaging/node.txt` and `packaging/fetch-node.sh`, then runs
`build-release.sh` in it as the invoking user. The checkout is always mounted
at `/build/quoro` and the cargo home at `/build/cache/cargo`, so the build paths
are the same on every host. Downloaded crates and npm packages are cached in
`target/release-container/`. It uses podman when installed, otherwise docker;
`QUORO_CONTAINER_ENGINE` picks one. The release workflow uses docker.

The image is not published: every build rebuilds it from the pinned inputs
(the layer cache makes that cheap). The image's own bytes may differ between
hosts (layer timestamps); what it contains does not, and only what it contains
reaches the release.

`build-release.sh` still runs directly on a host for local iteration, but it
warns that the result will not match the published release.

### Build script knobs

`packaging/build-release.sh` pins the rest. Each knob and why:

| Knob | Why |
| --- | --- |
| `SOURCE_DATE_EPOCH` from the tag's commit time | Timestamps embedded in the archive and honoured by tools that support the variable do not depend on when the build ran. |
| `LC_ALL=C`, `TZ=UTC`, `umask 022` | Locale, timezone and file modes cannot leak into output. |
| Pinned toolchain from `rust-toolchain.toml` | The compiler version is part of the build; a different rustc produces different bytes. The image carries exactly this toolchain; a host build installs it if missing. |
| Pinned Node.js from `packaging/node.txt`, sha256-verified by `packaging/fetch-node.sh` | The panel is built by Node; a different Node or npm produces different panel bytes, and those bytes are compiled into the binary. The build refuses a `node --version` that does not match the pin. |
| `npm ci --no-audit --no-fund` against `panel/package-lock.json` | The dependency tree is exactly the lockfile; `npm install` could resolve differently or rewrite it. |
| The panel is built before cargo | `rust-embed` compiles `panel/dist` into the binary, so the panel must be final before rustc runs. The build requires `panel/dist/index.html` afterwards. |
| `-C linker=rust-lld` | The linker ships with the toolchain, so the host's linker and its version are not part of the build. |
| `-C target-feature=+crt-static` | Produces a static binary; no dynamic loader or host libc at run time. |
| `--remap-path-prefix` for the checkout and `CARGO_HOME` | Absolute build paths in debug info, panic messages and embedded strings become `/build/quoro` and `/build/cargo`, so the build directory does not matter. |
| `CARGO_INCREMENTAL=0` | Incremental state changes codegen. |
| `CARGO_PROFILE_RELEASE_LTO=true`, `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1` | Removes parallelism and partitioning from codegen, which otherwise varies with scheduling. |
| `CARGO_PROFILE_RELEASE_STRIP=symbols`, `DEBUG=0` | Drops symbols and debug info whose contents depend on paths and toolchain build details. |
| `CARGO_PROFILE_RELEASE_PANIC=unwind` | Pinned explicitly so a profile change cannot alter codegen silently. |
| `CARGO_TARGET_DIR` fixed inside the checkout | Keeps the build self-contained and out of `~/.cargo`. |
| `CARGO_BUILD_RUSTFLAGS`, `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER` unset | An inherited wrapper or extra flags would change the compile commands. |
| `musl-gcc` + `-ffile-prefix-map` | C dependencies (ring, aws-lc, the bundled SQLite) are compiled by the image's `musl-gcc`; the image pins its version and the prefix map strips paths. Required inside the image. |
| `tar --sort=name --format=gnu --mtime --owner=0 --group=0 --numeric-owner --mode=...` | Archive entry order, timestamps, ownership and permissions are fixed instead of coming from the filesystem. |
| `gzip -9 -n` | No original file name and no gzip timestamp in the header. |
| `--locked` and a clean tree check | The dependency set and the sources are exactly what the tag says; a dirty tree is refused unless `QUORO_ALLOW_DIRTY=1`. |

`QUORO_SKIP_PANEL=1` and `QUORO_ALLOW_DIRTY=1` exist for local iteration only:
both print a warning and the result is **not** a release build.
`QUORO_DEV_WARM_POLICY=1` is for test-lab dev builds only: it turns on the
dev-only `dev-warm-policy` feature, which accepts `ha_policy: warm` before the
warm policy ships (ADR 0223), and prints the same warning. `quoro version`
reports it, and the release workflow fails a release whose binary does. Without
`QUORO_SKIP_PANEL`, the build refuses to run when the pinned Node.js is not
first on `PATH`; run `packaging/fetch-node.sh <dir>` and put `<dir>/bin` there.

## Verify a downloaded release

```sh
# from a directory holding the tarball, SHA256SUMS and the .sigstore.jsonl
packaging/verify-release.sh \
  quoro-0.1.0-x86_64-unknown-linux-musl.tar.gz v0.1.0
```

The script requires `gh` and does two things:

1. Checks the tarball's line in `SHA256SUMS` (when that file is next to it).
2. Runs the equivalent of:

```sh
gh attestation verify quoro-0.1.0-x86_64-unknown-linux-musl.tar.gz \
  --bundle quoro-0.1.0-x86_64-unknown-linux-musl.tar.gz.sigstore.jsonl \
  --repo OmarAlex24/quoro \
  --signer-workflow OmarAlex24/quoro/.github/workflows/release.yml \
  --source-ref refs/tags/v0.1.0 \
  --deny-self-hosted-runners
```

That binds the bytes to a workflow run in this repository, on this tag, on a
GitHub-hosted runner. Success prints `VERIFIED`.

For a dry-run artifact the source ref is a branch, not a tag, so it is verified
with `--dry-run-ref` instead:

```sh
packaging/verify-release.sh \
  quoro-0.1.0-x86_64-unknown-linux-musl.tar.gz \
  --dry-run-ref refs/heads/main
```

That succeeds with `VERIFIED (dry run from refs/heads/main, not a release)`. It
is not a release verification: the artifact was built and attested from a
branch, and the workflow never created a tag or a release for it.
`--dry-run-ref` accepts only `refs/heads/<branch>` and cannot be combined with
`QUORO_VERIFY_SOURCE_REF`.

## Dry run

The release workflow can be run without a tag to exercise the whole release
path before tagging (ADR 0082). A dry run builds, attests and uploads workflow
artifacts only; it never creates a tag, a release or a draft release.

1. Actions → Release → Run workflow, on `main` (or another branch).
2. Download the `quoro-<version>-dry-run-<sha>` workflow artifact.
3. Verify it:

   ```sh
   packaging/verify-release.sh quoro-<version>-x86_64-unknown-linux-musl.tar.gz \
     --dry-run-ref refs/heads/main
   ```

4. Install it with the installer's local-artifact path:

   ```sh
   QUORO_INSTALL_FROM=<dir> QUORO_INSTALL_DRY_RUN_REF=refs/heads/main installer/install.sh
   ```

   `QUORO_INSTALL_DRY_RUN_REF` tells the installer that the attestation is
   bound to that branch ref instead of a tag. A dry-run artifact is for testing
   the release path, not for a real installation.

## Reproduce a release

Needs an x86_64 Linux host with podman (preferred) or docker, git and curl,
and about 5 GB free where the work directory is created. That is `TMPDIR`
(default `/tmp`); `/tmp` is often a small tmpfs, so point `TMPDIR` at a disk,
for example `TMPDIR=$HOME/quoro-reproduce` (the directory must exist).

```sh
packaging/reproduce-release.sh v0.1.0
```

It fetches the tag into a temporary directory, rebuilds there with the clone's
own `packaging/build-in-container.sh` (so a tag is rebuilt with the image
definition it was released with), downloads the published `SHA256SUMS` and
compares hashes. It prints both hashes and `REPRODUCIBLE` or `MISMATCH`. Use
`--sums <path>` for an offline checksum file, `QUORO_REPO_URL` for a different
fetch source, `QUORO_KEEP=1` to keep the work directory and
`QUORO_CONTAINER_ENGINE` to pick podman or docker. The image stays in the
engine's image store; its tag is printed so it can be removed.

A dry-run artifact is reproduced from its commit (or branch) and the
`SHA256SUMS` from its workflow artifact; the version is the Cargo version, as
in the dry run:

```sh
packaging/reproduce-release.sh --ref <40-character commit sha> --sums ./SHA256SUMS
```

## Known limits

- **Build in the image.** Only builds made with
  `packaging/build-in-container.sh` match the published bytes. A host build of
  the same commit uses the host's C compiler and differs.
- **x86_64 hosts.** The image is linux/amd64. On another architecture the
  engine has to emulate it, which is slow and not tested.
- **The pinned sources must stay online.** Rebuilding the image needs the base
  image by digest from Docker Hub, the pinned snapshot from
  `snapshot.ubuntu.com`, `rustup-init` and the toolchain from
  `static.rust-lang.org`, Node.js from `nodejs.org`, and the crates and npm
  packages from their registries. If one of them disappears, an old release
  can no longer be rebuilt from scratch.
- **The first apt step skips TLS peer verification.** The base image has no CA
  bundle and the snapshot service is HTTPS-only, so `ca-certificates` itself
  is fetched without checking the server certificate. apt still verifies the
  signed index and every package hash, and the package is pinned to an exact
  version; every later download verifies TLS.
- **Signatures only exist for workflow builds.** Attestations are created by
  `.github/workflows/release.yml`, on tag pushes and on dry-run dispatches.
  Locally built tarballs are byte-identical but unsigned; `verify-release.sh`
  will reject them.
- **Bundles are per-artifact.** `gh attestation verify` with `--bundle` checks
  the repository and owner recorded in the certificate, not whether that name
  still belongs to the project. For a stronger check, omit `--bundle` and let
  `gh` fetch the current attestation from the API.
