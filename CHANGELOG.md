# Changelog

All notable changes to Quoro are recorded in this file, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Quoro is an experimental preview: until the first general release, any version may break compatibility.

Each entry links the pull request that made the change and, where one exists, the architecture decision record (ADR) behind it. The milestone each release belongs to is shown in the [roadmap's status table](https://github.com/OmarAlex24/quoro/blob/main/docs/product/roadmap.md#status).

## [Unreleased]

### Added

- **The fold of the promotion rebuild.** The control plane can now fold a followed change log into one row per entity, as `quoro cluster promote` will when it builds its database (`node-agent-protocol.md` section 7.3 step 4). A `create` replaces the row, and a column it lacks takes the column's default; an `update` merges over the row, into an empty one when there is none, so a field it lacks keeps its value; a `delete` removes the row and ignores its payload; a payload field with no column is ignored, so a whole-App payload writes an app's warm columns and a partial one keeps them. An entity that never received a `create` stops the fold with an error that names it and the `seq` of its first entry, and a row built again only from updates after a `delete` is left out and listed with the fields those updates wrote. A `create` whose key columns, joined with `/`, are not its `entity_id` does not stop the fold: its row is kept under its `entity_id`, and the `create` is listed with its `seq` for the caller to log. The fold returns every `delete` with its `seq`, and each row with the `seq` of its last `create`, which the schema's cascades need, and it keeps each column's declared type, `NOT NULL` and default for the insert. `backup_repositories.repo_key_enc` is always an empty BLOB. Nothing calls the fold yet: writing the new database, with its cascades and `meta`, comes in a later change ([#906], [#19], [ADR 0317], [ADR 0297], [ADR 0286]).
- **The fold of the promotion rebuild.** The control plane can now fold a followed change log into one row per entity, as `quoro cluster promote` will when it builds its database (`node-agent-protocol.md` section 7.3 step 4). A `create` replaces the row, and a column it lacks takes the column's default; an `update` merges over the row, into an empty one when there is none, so a field it lacks keeps its value; a `delete` removes the row and ignores its payload; a payload field with no column is ignored, so a whole-App payload writes an app's warm columns and a partial one keeps them. An entity that never received a `create` stops the fold with an error that names it and the `seq` of its first entry, and a row built again only from updates after a `delete` is left out. A `create` whose key columns, joined with `/`, are not its `entity_id` stops the fold too. `backup_repositories.repo_key_enc` is always an empty BLOB. Nothing calls the fold yet: writing the new database, with its cascades and `meta`, comes in a later change ([#906], [#19], [ADR 0317], [ADR 0297], [ADR 0286]).
- **`quoro cluster maintenance` opens a maintenance window before a planned restart of the primary.** Run as root on the primary's host, `quoro cluster maintenance [--duration <seconds>]` reaches the running primary over its local control socket, `/run/quoro/control.sock`, which only root and the service user may open: the file is mode `0600` and the primary checks each peer's uid. Its JSON lines carry a version, `v` 1, since the installer runs the new binary against the primary still running the release before; the primary refuses a request of another version, or of none, with an error that says so. `quoro.service` now gets `/run/quoro` from systemd (`RuntimeDirectory=quoro`). The primary asks its voters for support with `max_lease_ms` = `W` (default 180 s, at least `D` and at most 600 s; out of range is refused), and each voter gets that request at once. Once a majority supports `W`, it raises `leases.duration_ms` to `W` for every lease row that reads `expiring`, carries no unsettled mark and is not revoked. Once that raise is replicated over every machine with the `node` role, it answers the renewals of those leases with `W` while the window is open, and with `D` until then. The command succeeds once the newest answer to every one of them carried `W` (a holder counts its validity from its newest answer) and no other lease that is not revoked reads `expiring` or carries the unsettled mark, and prints until when the window is open and until about when every lease is covered, one margin early. It fails with the reason and a non-zero exit when no majority supports `W` within `D / 3` plus one margin (6.5 s), when the raise is not replicated in that time, or when the window does not cover a lease: one whose holder has not renewed in that time, one whose newest renewal was answered with `D`, a marked one, or one that turned `expiring` after the raise. A `W` answer needs the row to still read `expiring`, unmarked, unrevoked and storing at least `W`, and a majority to support `W` at that moment; otherwise the renewal is answered with `D`. When the window does not cover a lease, the command prints each one with why, after waiting for the window's own leases, and the window stays open, so the leases already answered keep their longer validity. The primary writes one `cluster.maintenance` audit record per window it tries to open: `ok` once it opens, also when it does not cover every lease, with the raise's newest change-log write as `change_seq` when the raise wrote one, and `error` with the reason otherwise. The window closes `W` after it opened, with `quoro cluster maintenance --end`, which writes a record with `params` `{end: true}`, or at the primary's next start, whichever comes first. Renewals are then answered with `D` again, and every `W` answer keeps its longer gate; once those gates have passed, the stored duration goes back to `D`. The installer runs the command before it restarts `quoro.service`. When the command fails, the installer says that the window does not cover every `warm` app, that an app it does not cover fences if the restart takes longer than about `D`, and goes on with the upgrade. A primary of a release before this one has no control socket: on the first upgrade from one, the command says that no maintenance window can open because the running primary has no control socket, and the installer that no maintenance window covers the `warm` apps ([#912], [#764], [ADR 0171], [ADR 0268], [ADR 0289]).
- **An operator can remove a node.** `DELETE /api/v1/nodes/{node_id}` (`removeNode`, scope `node:remove`) is now served. It is human-only: an agent is refused with `forbidden` and `reason: human_only`. An unknown node answers `404`; a node already removed, the node that holds the primary status, and a node that still hosts an instance it reports `running` answer `409 conflict`. An instance of a node that is not connected reads `unknown`, so it does not hold the removal back. An already removed node is refused before the voter-set gate is read. Removing a voter passes the voter-set gate: it answers `409` until a majority of the voters the change log gives at the current voter-set version holds that version, and while the `nodes` rows and the change log disagree on another machine. Removing the machine they disagree on is the one change the gate lets through, since its removal entry ends the disagreement, also for a row already marked `removed` without its entry. Removal is never refused for leaving fewer than three voters, and has no `force`. For a connected node, the primary first records each lease the node has not released as revoked, sends a `lease_revoke` for each, and waits for every answer. Only an `ok` answer releases a lease. A `fence_failed` answer, recorded or not, a refused revoke, a session that ends first, or no answer within 180 s answers `409`, and the node is not removed; its leases stay revoked, and a retry goes on from there. A lease that another node's failed fence lists also answers `409`, naming that node. For a node that is not connected, the primary raises the token of every lease row that names it and that it has not released, a row an earlier attempt revoked included, as declaring it lost does; a row already revoked at the highest token, 2^53 − 1, is left as it is, since no grant can follow it. A failed fence the node reported that the primary could not record is written into the node's `fence_failure` in the removal's transaction and travels in the removal's own change-log entry, so it survives a restart of the primary and no follower holds the removal without it; if that write fails, nothing is removed. In one transaction the node then turns `removed`, its change-log entry becomes the removal entry that the voter set and the replication of lease writes read, the records of its quarantined copies are dropped (the files stay on its disk), its custody seals are deleted, and the audit record `removeNode` with `params` `{node_id}` names that entry. From the commit on, the primary reads the node as not connected, also while its session is still ending. After the commit, the node's session ends with the fatal `error` `node_removed` and nothing after it. A `hello` from a removed node records nothing and gets the same error, so a node that dials during the removal is never written back to `connected`. The call answers `202` with the node. A connected node's `lease_revoke` carries reason `declared_lost`, since the contract names no reason for a removal yet ([#909], [#740], [ADR 0030], [ADR 0183], [ADR 0261], [ADR 0280], [ADR 0321]).
- **A planned switchover of a warm app.** `POST /api/v1/apps/{app_id}/switchover` (`switchoverApp`, scope `app:failover`) is now served. Before anything is written, the call refuses with `not_warm`, `in_progress` (a failover or switchover of the app runs, or a grant of its lease waits), `validation_failed` for a `node_id` that is not `App.warm.node_id`, `not_in_sync` unless `App.warm.state` is `in_sync`, `node_disconnected`, `fence_failed` or `no_support`, in that order. An app whose lease is revoked is refused with a plain `conflict` before `not_in_sync`, and `failoverApp` to the same warm node completes its move. Then the call writes its audit record and answers `202`, and the switchover runs on its own: the source gets `switchover_freeze` for the app's VM, and the primary waits for its answer for four replication intervals, at least 120 s and at most 600 s. Once the source answers with the final snapshot, the primary checks both nodes, that the warm node reports that snapshot (waiting up to 35 s for its report), the fences and majority support again, revokes the lease and moves it to the warm node as a failover does, and emits `app.switched_over` with that snapshot's `snapshot_seq`. A freeze that fails or times out, or a check before the revoke that fails, sends the source `switchover_thaw` and emits `app.switchover_failed` with `step` `freeze` or `revoke`; nothing moves. A failover and a switchover of one app answer `in_progress` while the other runs, or while a thaw of the app waits for its answer. A source that reports `frozen: true` while no switchover of its app runs, as after a primary restart, gets `switchover_thaw`. A `command_result` now carries `snapshot_seq`, and the protocol code `replication_failed` is known ([#894], [#735], [ADR 0177]).
- **A node forgets a quarantined copy whose clone is gone before it was hashed.** A returning source used to keep reporting such a copy without a hash, retrying its hash forever, and no operator could delete it, since the primary never recorded it. When the hash finds no file, the node agent now forgets the copy's record and its kept snapshot, without touching any file, only when the engine answers `NotFound` for the clone; another kept snapshot of the volume answers the engine or, when none does, the engine finds the volume's live file; one open handle of the clone's directory shows the clone missing and that kept snapshot or live file there as a regular file; and the record still has no SHA-256. A copy with neither another kept snapshot of its volume nor its live file keeps its record, and so does one whose record and kept snapshot name different files. One whose live file a VM attaches keeps it until the VM is gone, and one whose volume another warm call holds keeps it until that call ends: the checks take the volume's lock without waiting for it, so they never make the commit of a received copy fail. Otherwise the record stays, with a warning that says why, and the hash is tried again; a volume pool that does not mount never counts. The next status report no longer lists the copy ([#878], [#877], [#882], [#880], [#884], [#883], [#926], [#762], [#834], [ADR 0215]).
- **The primary answers the N+1 indicator.** `GET /api/v1/cluster/capacity?lost_node_id=` (`getClusterCapacity`, scope `cluster:read`) is now served, and the MCP tool `get_capacity` reads it. It answers whether the apps of one node would fit on the others if that node were lost, or which resources are missing. It takes the apps with an instance meant to run there (`desired_status` `running`) or a volume there. A stateless app that keeps an instance on another connected node with the `node` role loses one replica (`keep`); an instance on a node that is not connected does not count. One whose only instance was there needs a new one (`start`). A `warm` app starts on its warm node, which already holds the disk (`failover`), and any other stateful app needs a restore of its latest backup (`restore`). The apps that need a node are placed largest first, by memory, then vCPUs, then disk, on the connected node with the `node` role that has the most memory left and room for the whole app, within the app's placement. A node's room is its capacity minus `Node.allocated`. An app with no succeeded backup (`no_backup`), or a `warm` app whose warm node reports no complete copy (`no_warm_copy`), cannot move and does not make `fits` false; an app that finds no room (`no_capacity`) does, and its resources are summed in `missing`. A warm copy is known from the warm node's reports, which the primary holds in memory, so after a restart of the primary a `warm` app reads `no_warm_copy` until its warm node reports again. A `warm` app whose warm node is not connected reads `no_capacity`, and its memory and vCPUs count in `missing`, although capacity on other nodes cannot help it: it can start only on its warm node. An agent whose grant selector is narrower than `{"all": true}` sees only the apps the selector matches, and `fits` and `missing` count only those. Nothing is reserved and no event is emitted. A missing or malformed `lost_node_id` answers `422`, and an unknown or removed node `404`. The Nodes page's verdict and "Simulate losing" now work against a real cluster with more than one node ([#864], [#717], [ADR 0021], [ADR 0178], [ADR 0217]).
- **A quarantined copy of a volume that is gone is recorded.** A returning source can report a quarantined copy after its volume was deleted, or while it reads `deleting`. Such a copy used to be skipped with a warning. The first report that lists it with its `sha256` now writes the system audit record `volume.quarantine` and emits `volume.quarantined`, with the same fields as for any copy. It does so once per `quarantine_id`, also across a restart of the primary, and writes no `volume_quarantines` row. The copy is therefore not listed in `Volume.quarantines`, `deleteVolumeQuarantine` cannot reach it, and it never blocks a delete; the operator removes its file on the node. A copy that names another app than its volume's is still skipped ([#867], [#865], [ADR 0316]).
- **The panel shows a warm app's copy.** For an app whose `App.warm` is not null, the Storage tab now has a Warm copy box: the copy's state as a tag that always carries its word (`Syncing`, which pulses, `In sync`, `Lagging` or `Failed`), the warm node with a link to it and whether the scheduler picked it or an operator pinned it, or `No eligible node`, the primary's error in full, what a failover now would lose from `lag_s` as the primary measured it, the last shipped snapshot and when it completed, the snapshot interval and the extent count of the newest snapshot. A progress field the primary leaves null is not shown, and a copy with no complete snapshot reported says so, which also covers the time after a primary restart. The app's card on the canvas gets one footer row with the copy's state, its warm node and its lag, or the first line of the error; the card's lamp stays the app's status. For a warm app the panel reads the app at least every `interval_s`, never more than once every 5 s, and not at all while the browser tab is hidden. The mock API serves warm apps in every state, with progress that moves with the clock ([#839], [#562], [ADR 0173], [ADR 0174]).
- **The warm node keeps its copy as its base when a failover makes it the source.** When the desired state makes a node the source of a volume it holds the warm copy of, its node agent now keeps that complete copy as its base before the volume is ready, and so before the VM starts on it: a snapshot numbered with the copy's `snapshot_seq` and carrying its cell hashes, the common base a returning source resyncs from. The copy's file becomes the node's volume and its warm-target record goes. The sender takes no snapshot until the base is kept, then numbers its snapshots after the copy, and its first stream names the copy as its base instead of shipping a full copy. A copy a crash or a failed swap left pending is resolved first, by the warm receiver's pass, since no stream comes for it any more. A warm node with no complete copy creates neither the volume nor the VM and reports the volume `failed` with the reason, where it would have started the app on an empty volume. The primary's side of the failover is not part of this change ([#696], [#694], [ADR 0175]).
- **Nodes keep a mark of the change log they acknowledged.** A machine with the `node` role now keeps, in a file next to its credential and outside its database, the newest change-log entry it acknowledged, and syncs it to disk before it reports that entry to the primary. A copy that went back, as after a lost `node.db`, therefore reads as below the mark, which a promotion will check. When the primary declares a node's copy diverged, the node records that it is following again before it moves the copy aside, and keeps that state until its new copy reaches the primary's newest entry at that time; an agent stopped in between finishes the move when it starts again. One limit remains from v0.3.0, which moved a diverged copy aside without recording that the node was following again: a node that was refollowing when it was upgraded is not known to be refollowing, so its first `hello` sets the mark to the partial position it had reached ([#699], [ADR 0261]).
- **The API and the panel show how far each node is behind the change log.** `GET /api/v1/nodes` and `GET /api/v1/nodes/{node_id}`, the MCP tools `list_nodes` and `get_node`, and the other responses that return a node (setting its tunnel, acknowledging a failed fence) now report each node's acknowledged change-log `seq` as `log_seq` and how far it is behind the primary's newest entry as `log_lag`. `log_seq` is the newest acknowledgement the primary holds in memory, or, after a restart of the primary, the position stored for the node. `log_lag` is null for a machine without the `node` role, which does not follow, and is always present. The panel's node card shows it in one line for a machine with the `node` role: whether its change log is in sync, or how many entries it is behind ([#74], [ADR 0227], [ADR 0301]).
- **The primary counts voter support, and `ha_ready` can be true.** Every machine with the `node` or `witness` role now gets the voter set in its desired state: `spec.votes`, whose version is the change-log entry that last changed the set, and `spec.witness` on a witness. After a voter has stored that desired state, the primary asks it for support every 5 s, and counts a majority of the whole voter set, connected or not, from the answers that carry its current voter-set version. Each answer counts for 13.5 s from when its request was sent, measured on `CLOCK_BOOTTIME` ([ADR 0263](https://github.com/OmarAlex24/quoro/blob/main/docs/adr/0263-the-primary-measures-its-support-window-p-send-on-clock.md)). A `stale_term` from any node stops all support until the primary restarts, and a restarted primary holds none until its voters answer it again. `Cluster.votes.ha_ready` is now true while at least three voters are enrolled and a majority supports the primary. With that support the primary answers renewals of `expiring` leases and sends an `expiring` new token over a lease row that already stores `D`; grants that wait for replication stay held ([#703](https://github.com/OmarAlex24/quoro/issues/703)). A host without `CLOCK_BOOTTIME`, such as a macOS dev build, counts no support (`node-agent-protocol.md` section 8.8, [#686](https://github.com/OmarAlex24/quoro/issues/686)).
- **Failover of a warm app.** `POST /api/v1/apps/{app_id}/failover` (`failoverApp`) moves a `warm` app's lease to its warm node, which starts the app on its last complete copy. Before anything is revoked or written, the call refuses with `not_warm`, `in_progress`, `validation_failed`, `no_copy`, `node_disconnected`, `fence_failed`, `no_support` or `lease_held`, in that order. A connected source is revoked first, and its app's VMs are stopped in the same transaction. The call waits for the source's answer, then for the lease's gate, at most `duration_ms + 2M`. One change then writes the warm node as holder of an `expiring` lease at a higher token, moves the volume and the app's VMs there, makes the old source the app's warm node, and emits `app.failed_over` with the copy's `snapshot_seq`; the grant follows the commit. A client that gives up does not stop a failover halfway. A failover whose grant must wait for replication (a lease row with the unsettled mark, or one that does not read `expiring` for at least the lease duration) writes the row with the mark set, moves everything else, and answers `202`: the primary holds the grant and sends it once every machine with the `node` role has acknowledged the write and a majority of voters supports it. `App.lease.grant_pending` and `App.lease.grant_waiting_on` show the wait, `app.failed_over` carries `grant_pending: true`, and a second failover of the app answers `in_progress` until the grant goes out ([#726], [#720], [#703], [ADR 0175], [ADR 0292], [ADR 0303]).
- **Nodes keep a custody key and report its public half.** A machine with the `node` role now keeps an X25519 custody key in `custody.key` next to its credential, mode `0600`, generated when it enrolls with the `node` role or, on a machine upgraded to this release, when the agent starts; a key that exists is never replaced, even by a key created at the same moment, and an unreadable one is left as it is and logged: the node still connects and sends `hello` without the key, and promotion from that machine is refused until the key can be read. The machine sends the key's public half as `custody_public_key` when it enrolls and in every `hello`; edge-only and witness-only machines keep and send none. The primary binds the key and seals the cluster keys to it, as the entry below says ([#727], [ADR 0231]).
- **The primary binds each node's custody key and seals the cluster keys to it.** The first custody key a machine with the `node` role reports in `hello` is stored for it and never replaced; the primary binds the key from the machine's first `hello`, not from its enroll request. A `hello` with a different key is answered with the non-fatal `custody_key_changed`; the session goes on, nothing is sealed to the new key, and the change is recorded once, with the audit record `node.custody_key_changed`. The primary seals its signing key, its data-encryption key and its TLS certificate and key to each such machine in the replicated table `node_key_custody`, when it first stores the machine's key and again at every start, which also deletes the seals of retired keys and removed machines. Edge-only and witness-only machines get no seal. `Node.custody` now reads `sealed`, `pending`, `none` or `key_changed`, or null without the `node` role, and `Cluster.signing_key_id` names the current signing key ([#727], [ADR 0180], [ADR 0231]).
- **A runbook for the M5b demo.** The Guides part of the documentation site has the [M5b demo runbook](https://github.com/OmarAlex24/quoro/blob/main/docs/guides/m5b-demo-runbook.md). It maps each of the 13 boxes of the milestone's Definition of Done to a step, and has a pre-flight checklist. Then come the six demo steps: the witness, a `warm` app, the cut and the failover, the return of the cut-off node, the planned switchover with the N+1 indicator, and the promotion. Each step gives the command or panel action, the expected result, the evidence to keep and what to do if it goes wrong. The runbook lists the operations the primary does not serve yet with their issues, and the points the contracts leave open ([#736](https://github.com/OmarAlex24/quoro/issues/736)).
- **The primary records a returning source's quarantined volume copies, and only a human deletes them.** A node that lost a `warm` app's lease to a failover keeps its divergent writes as a quarantined copy and lists it in `status_report.quarantines`. The primary now records each copy the first time a report lists it with its `sha256`, in one transaction with the system audit record `volume.quarantine` and the `volume.quarantined` event, and lists it in `Volume.quarantines`, oldest first, as `kept` or `deleting`. `deleteVolume` and `deleteApp` answer `409 conflict` with `reason: has_quarantines` while a copy of the volume is recorded, or listed by a node that is still hashing it. The new human-only `DELETE /api/v1/volumes/{volume_id}/quarantines/{quarantine_id}` (`deleteVolumeQuarantine`, scope `app:delete_quarantine`) marks the copy `deleting` and sends it to its node in `spec.quarantine_deletes`; the record goes once the node stops listing the copy. No node keeps a quarantined copy yet: that is the node's side of the return path, which comes next. Until `removeNode` exists, nothing clears the record of a copy on a node that never comes back ([#738], [#732], [ADR 0176], [ADR 0215]).
- **A grant that must wait is written and held until it may go out.** A new token whose grant must wait (a `local` one for a `warm` or `hot` app, a `local` one over a row that reads `expiring`, an `expiring` one that raises the stored duration, one without voter support, or any over a row that already carries the unsettled mark) is now written with the mark set, and the primary holds its grant instead of refusing the operation. `createVolume` answers `201`, a `warm` app's restore completes, and a regrant writes its token, where before they wrote nothing and `createVolume` answered `409`. The held grant goes out on the holder's session only once every machine with the `node` role has acknowledged the write, a majority of voters supports it and its gate allows it, all checked again in the transaction that sends it; the new holder's gate is measured from the send. A node's `hello` position counts as an acknowledgement only once every revoke sent on that session is answered, and `log_diverged` drops it. A removed machine leaves the required set once the others have acknowledged its removal. `Lease.grant_pending` and `Lease.grant_waiting_on` now show the wait, and `Lease.unsettled` and `Lease.local_pending` the mark. A restarted primary rebuilds the held grants from the rows and the change log, gives every marked row its start gate (the longest duration for a marked `local` row with none stored, so its grant can wait up to 720 s), and decides at each node's next session from what its `hello` lists whether to send the grant, revoke first, or send nothing. A node that a marked row does not name and that lists the lease `held` or `uncertain` has the row raised above its token and recorded revoked. The writes that clear the mark are not part of this change ([#703](https://github.com/OmarAlex24/quoro/issues/703), [ADR 0280](https://github.com/OmarAlex24/quoro/blob/main/docs/adr/0280-every-grant-of-a-marked-lease-waits-until-every-node-holds.md), [ADR 0285](https://github.com/OmarAlex24/quoro/blob/main/docs/adr/0285-a-volume-restore-that-turns-an-expiring-lease-row-local-at.md), [ADR 0292](https://github.com/OmarAlex24/quoro/blob/main/docs/adr/0292-failoverapp-answers-202-at-once-while-the-grant-of-a-marked.md), [ADR 0295](https://github.com/OmarAlex24/quoro/blob/main/docs/adr/0295-a-restarted-primary-sends-a-marked-row-s-pending-new-token.md), [ADR 0299](https://github.com/OmarAlex24/quoro/blob/main/docs/adr/0299-a-node-s-hello-counts-toward-a-marked-row-s-grant-only-once.md)).
- **A machine can gain or lose the witness role, and a witness-only machine can join.** `POST /api/v1/nodes/{node_id}/roles` (`updateNodeRoles`, human-only scope `node:roles`, audited) adds or removes the `witness` role of an enrolled machine, typically an edge that becomes the third voter, without enrolling it again. Adding a role the machine has, or removing one it lacks, answers `200` and changes nothing. A change that adds or removes a vote answers `409 conflict` until a majority of the current voters has acknowledged a desired state carrying the current voter-set version, and removing a vote answers `409 conflict` when fewer than three voters would remain while any `expiring` lease exists, unless the request sets `force`. The enrollment of a machine with the `node` or `witness` role follows the same rule: while the previous voter-set change has not reached a majority, it answers `409` without consuming its join token, and `quoro join` can be run again with the same token. So a voter enrolled with `quoro join` must have started its node agent (`quoro node`) before the next voter can enroll. The machine acts on its next desired state, which carries `spec.witness` and the new `spec.votes`, and a new witness gets a mesh address if it has none. `quoro join --role witness` enrolls a witness-only machine, which runs the node agent with no engine and starts no VM, as an edge-only machine does ([#687](https://github.com/OmarAlex24/quoro/issues/687), [ADR 0170](https://github.com/OmarAlex24/quoro/blob/main/docs/adr/0170-witness-role-any-enrolled-machine-can-add-the-witness-role.md)).
- **The panel shows the voters and offers a witness when HA needs a third vote.** The Nodes page now opens with the cluster's voters from `Cluster.votes`: each one by name, with its roles and whether it is connected, and the count against the votes HA needs. It reports each voter's answer, whether the grants form a majority of the whole voter set, and when the old primary's grants have passed their gate: the latest receipt time plus `lease_wait_ms` over the grants. A voter that cannot be reached, does not answer in time, answers anything but `200`, or answers with a term above the ceiling gives no answer. The client writes nothing to the node's store. The command itself comes later ([#911], [#19]).
- **No machine adopts or records a term above 2^53 - 1.** A node answers a `welcome` whose term is above the ceiling with `bad_message`, adopts nothing from it (no term, schema version, addresses or primary) and dials again. It answers a `desired_state` or `support_request` above it with `bad_message` and changes nothing; such a `desired_state` used to draw `bad_signature`. The node's store refuses to write a term above the ceiling. The primary treats an `error` whose `term` is above the ceiling as malformed: it logs it, does not demote itself and records nothing from it, and a demotion never records `demoted_by_term` above the ceiling. The candidate and restore paths of the ceiling come later ([#908], [#862]).
- **The primary logs whether promotion votes are open.** At its start, and then each time the result changes, the primary logs at `info` `promotion votes open`, or `promotion votes closed` with every machine with the `node` role that keeps them closed and the mesh rules version it reported, or `not reported`. A change of the change log's head alone, or of the voter set alone, logs nothing ([#901], [#899]).

So on a cluster with more than one node, the Nodes page does not show its sentence on whether the cluster can lose its biggest node.

- **Health checks restart a VM that stays unhealthy.** When an app VM's health check fails `failures` times in a row outside its start period, the node now stops the VM and starts it again in place, besides reporting it `failing` and emitting `app.down` (`node-agent-protocol.md` section 6.3). The restart goes through the crash path. It waits out the crash backoff, which doubles from 1 s to 5 min, so a VM that never gets healthy is restarted less and less often. The backoff resets only once the VM has run 10 minutes without a failing check. The restart counts in `restart_count`; `restart_generation` stays as it was. Failed probes in the first `start_period_s` after each start, 30 s by default, do not count. One incident spans the restarts: one `app.down`, then `app.up` once the VM passes again. - **A host suspend counts against `expiring` leases.** The node measures lease time on a clock that keeps counting while the host is suspended (`CLOCK_BOOTTIME` on Linux). Its timers run on the monotonic clock, which stops during a suspend, while the primary's gate keeps running. So the node checks at least every 250 ms, and at once when the host wakes, how far `CLOCK_BOOTTIME` has moved beyond that clock. It then moves every `expiring` lease's deadline, renewals and pending renewals earlier by the difference. A lease whose deadline passed during the suspend expires and is fenced as soon as the host wakes, with no graceful stop, and so does one a revoke reaches first. No stateful start passes in between, and the node is not marked failed. The deadline a held lease stores for an agent restart now comes from the `CLOCK_BOOTTIME` reading taken when its renewal was sent, not when the answer arrived, so a suspend between the two cannot make it later ([#452], [#446], [ADR 0240]).

- **Fence events name the lease's token and the stopped VMs.** A node's `node.fenced` and `node.fence_failed` events now carry `fencing_tokens`: the token the node held for each fenced lease, the same one as in the fence's local record. When a revoke with a higher token joined a running fence, the event carries that revoke's token. `node.fenced` also carries `vm_ids`, the VMs the fence stopped. The failed fences an upgraded agent reports again carry their recorded token too ([#445], [#442], [#436]).

- **Warm volume calls in the engine.** The engine trait gains the calls warm replication is built on: `volume_changed_ranges` compares the extent maps of two reflink snapshots of a volume and returns only the byte ranges that differ (a full copy when there is no base or the maps cannot be compared), `stage_volume`, `commit_staged_volume` and `discard_staged_volume` build a volume's next copy beside the last good one and swap it in with one rename, and `pause` and `resume` freeze a running VM. A volume can now keep several snapshots, each in its own file. Nothing calls these yet; replication between nodes comes next ([#389], [#390], [ADR 0172], [ADR 0173]).
- **Snapshots that outlive a restart.** The node agent now records in its store the volume snapshots it must keep, such as a warm volume's base, and the engine's start-up sweep removes only the snapshots the store does not record. Until the store records every snapshot file left on the node, which is the case on a new node and after an upgrade, the sweep removes none. After a lost or re-created store it keeps every snapshot until an operator removes the ones it does not know, so a copy that might hold data is never deleted. M5a's snapshot name is still always removed ([#415], [ADR 0172], [ADR 0173]).
- **Warm replication receiver.** A node that holds the warm copy of an app's volume now listens for the source's replication streams on its mesh address (TCP 51822 by default). Before it writes anything, it checks that it is the volume's target, that the stream comes from the source's mesh address, and that it carries the app's lease and a fencing token no lower than any it has seen, so a source that lost its lease cannot overwrite the copy a failover would start from. It writes each stream into a staging file, checks every block's hash and the copy's root hash, and swaps the file in only when the whole stream is good: a stream that is cut short or fails a check leaves the last complete copy as it was. The copy and any refused stale stream are reported in `status_report.warm`, never as a volume ([#416], [ADR 0173]).
- **Warm replication sender.** The node that holds a warm app's lease now snapshots the volume every `interval_s` (30 s by default) and ships what changed since the last copy the target confirmed, or a full copy when it has none. It snapshots and ships only while it holds the lease with the token its desired state names, so a node that lost its lease sends nothing; it streams from its own mesh address, one volume at a time per target. It keeps only that last confirmed snapshot and the one it is shipping, and both survive an agent restart, so replication resumes without a full copy. A node that snapshots by pausing and copying is never a source. Each volume's last confirmed snapshot, when it was taken and confirmed, and the last error are reported in `status_report.warm`. Nothing turns it on yet: the primary sends no warm entry until the warm policy lands. If a node is rolled back to v0.2.0, its start-up sweep may remove the kept snapshots; after the next upgrade the source then ships one full copy ([#417], [ADR 0173], [ADR 0210]).
- **Standby VMs on the warm node.** A `spec.vms` entry can carry `standby: true`: the warm node of a warm app prepares that VM's image, so a failover does not wait for a pull, and creates and starts nothing, whatever lease it holds. It reports the VM `stopped`, and counts only its disk in its allocated capacity. The image is prepared after the VMs that run and their routes, and a failed preparation holds the revision back and is tried again after 60 s. A build's output is never pulled, so a standby VM of a built image is not prepared. A VM the engine already holds under a standby id is left as it is for now and holds the revision back. Nothing sends `standby` yet: the primary sends it once the warm policy lands ([#530], [#481], [ADR 0174]).
- **The warm node of a `warm` app, in the test-lab build.** In a build with the dev-only `dev-warm-policy` feature, `updateApp` now chooses the warm node of an app that becomes `warm`, and takes its settings. Every other build still refuses `warm` and its settings, as before, until the last warm PR turns them on. An app can become `warm` only with an attached volume on a node that snapshots with `reflink`, another eligible node, and no Git source ([ADR 0265]); otherwise the request answers `validation_failed`. An eligible node is connected, has the `node` role and a mesh address, snapshots with `reflink` and is not the volume's node. The app's placement does not narrow the choice ([ADR 0275]). The scheduler picks the node when no pin is given, spreading copies over the nodes that keep the fewest. `warm.node_id` pins an eligible node; `null` hands the choice back to the scheduler, which keeps the current node while it is eligible. `warm.interval_s` sets the interval. An app that leaves `warm` loses its warm node and pin and keeps its interval. Every 15 s the primary picks another warm node only when the current one is removed, loses the `node` role, snapshots with `pause_copy` or becomes the volume's node. A disconnected node, or one with no mesh address, stays the warm node and shows `failed`. A pin lasts until its node is removed ([ADR 0276], [ADR 0278]). Each change emits `app.updated` with `warm` in `changed`. It also wakes the volume's node, the old and new warm nodes and every node that still reports a copy of the app, so the new node gets its copy and an old copy is deleted once no failover can need it, also after the app went through a time with no warm node. `ha_cost.warm` gives the same availability and reason. It reserves disk only, the volume's size plus the root disk, and stores the warm copy's last reported allocated bytes, or the volume's before the first report. It starts in an estimated 10 s, and pauses nothing ([#632], [#611], [ADR 0277]).
- **Voters are mesh peers, and the warm node admits the replication stream.** Every two voters, the machines with the `node` or `witness` role, now get a WireGuard peer entry for each other. So the two nodes of a warm volume reach each other directly, and a cluster without an edge gets a mesh between its voters. Two witness-only machines are not peers; an edge that gained the `witness` role counts as one. Neither are two voters that both have no endpoint. A pair the star already joins keeps its single entry. A voter's endpoint is the source address of its session, with the mesh's listen port as the port. When that address is loopback or unspecified, the first non-loopback IPv4 host the primary advertises is used instead, as for the edge. A voter has no endpoint until the primary has seen its session since it started. Every entry between two voters carries a keepalive of 25 s. The warm node of a volume gets an `allow` entry for the source's mesh address on the replication port. The node agent's firewall now admits that stream to the host's own mesh address; before, it dropped it. The node agent also sets a peer's endpoint only when the peer is new on the device or the spec changed its endpoint, so the re-apply every 60 s no longer overwrites an address WireGuard learned when the peer roamed ([#671], [#650], [ADR 0266]).
- **An app's change-log entries keep its warm settings.** The app entries that carry the whole app now also carry `warm_node_id`, `warm_node_pinned` and `warm_interval_s`, beside the App fields, with `warm` null. They are written when an app is created or updated, when a restore moves it to another node, when its volume is created or the volume's deletion ends its `stateful` flag, and when the primary picks another warm node. A primary rebuilt from the log then keeps each `warm` app's warm node, pin and interval, which a failover needs. The entries that carry only the changed fields, and the delete entry, are unchanged ([#671], [ADR 0286]).
- **The primary's side of warm copies.** For a `warm` app the primary now sends the volume's node its `spec.volumes[].warm` entry as the source. It sends the warm node a `present` entry for the copy, and the app's VM as a `standby` entry, on the source VM's digest and with the app's lease. A pair needs both nodes to snapshot with `reflink` and to have a mesh address. A copy a node reports holding gets a `deleted` entry only once no failover can need it: its volume is being deleted, or the app left `warm` or moved to another warm node while its source is healthy. While a pair is only incomplete, as after a fence or a restore, or while the source's volume has failed, the warm node keeps its copy. When one side's entries change, such as a new token or a redeployed source VM, the other side's snapshot is rebuilt too, also when the change happened while that side was disconnected. `App.warm` now shows the copy's progress from the two nodes' newest `status_report.warm`, which the primary keeps in memory only: the last shipped snapshot, the lag on the primary's clock, the extent count, and `syncing`, `in_sync`, `lagging` or `failed` with the reason, including a warm node that cannot be one. An app that is not `warm` carries `warm: null`. After a primary restart these fields are null until the nodes report again. Nothing makes an app `warm` yet, because `updateApp` still refuses the policy ([#556], [#532], [ADR 0173], [ADR 0174]).

- **Expiring leases on the node.** The node agent now runs the `expiring` lease mode of section 8.4. It renews each such lease every third of its duration through its session, and counts a lease as valid only from the send time of a renewal the primary answered. A lease whose renewal is late, or whose session is lost, goes `uncertain`: its VMs keep running and nothing new starts for it. At the lease's deadline the node stops every VM bound to it within the margin `M` (a 1 s graceful stop, then a 0.3 s forced one), before the primary may grant the lease to another node. A held lease survives an agent restart on the same host boot: its deadline is converted to `CLOCK_BOOTTIME` once, when a renewal is answered, so a suspend after that can only shorten it, and after a reboot the lease comes back expired and is fenced. The primary grants no `expiring` lease yet; warm apps bring that. The M0 lease agent, which only tests used, is removed and its tests are ported to the lease service ([#431], [#75], [ADR 0072], [ADR 0225]).

- **Acknowledging a failed self-fence.** When a node cannot confirm that a VM stopped during a self-fence, including when it cannot list the engine's VMs, it marks itself failed and starts nothing stateful. Until now nothing could clear that mark, and the primary did not record the failure, so it could grant the lease again. The primary now lists the lease, app and VM ids in the node's `fence_failure` (`GET /api/v1/nodes/{node_id}`) and grants none of those leases until a human calls `POST /api/v1/nodes/{node_id}/fence-ack` with exactly the listed lease ids, after checking out of band that the VMs are stopped. Agents are refused with `human_only`, and the call is audited. The acknowledgement increments each lease's fencing token and reaches the node at once, or at its next session before its desired state; the node then clears those failed fences, and its failed mark once none remains ([#423], [#391], [#399], [ADR 0074], [ADR 0079]).
- **Nodes keep a copy of the change log.** The primary now sends its change log to every machine with the `node` role, its own host included, one batch of at most 500 entries at a time. The node checks each batch against the hash chain, stores it in its own database and only then acknowledges it. A node whose copy no longer matches the primary's writes that copy to a file under `quarantine/` in its data directory and receives the log again from its first entry. This is groundwork for promoting a node to primary in M5b: nothing reads the copy yet, and the API does not show a node's lag yet ([#668], [#697], [ADR 0179], [ADR 0227], [ADR 0261]).

A lease granted for 5 000 ms or less never leaves that much, and starts no stateful VM. Right after a renewal with `D` = 15 000 ms about 13.5 s remain, so the check holds back no start in steady state. The start check now reads the lease's mode and its answer in one look at the lease table ([#507], [#483], [ADR 0242]).
- A VM whose start failed, including a start that returned `Timeout` because the guest was not running by its bound, was started again on the next pass of the reconciler, at once or within 2 s. Under an `expiring` lease's 3 s bound, a VM that always boots slower was booted and killed every few seconds. A failed start now waits out the same backoff as a crash restart before the next try: 1 s, doubling to 5 min, reset after 10 minutes running. The wait counts from when the start returned, for a crash restart too. A successful start clears it, and so does an operator's restart (a new `restart_generation`), which runs at once. A failed start is not counted as a restart ([#493], [#462]).
- The Cloud Hypervisor backend took any error reading a VMM's `/proc/<pid>/stat`, such as `EMFILE` or `EACCES`, for a process that is gone. A forced stop then reported the VM stopped without a pid, which a fence takes for proof, so a node could report `node.fenced` while the VMM still ran. `SIGKILL` was also skipped, and an agent that restarted forgot a running VMM. Only `ENOENT`, `ESRCH`, a zombie or another process with the pid now count as gone. Any other error keeps the VMM: a forced stop sends no signal to a pid it cannot tie to the VMM and fails with the reason, so the fence reports `node.fence_failed`, and a restarted agent exits with status 75, naming the VM, so systemd starts it again, rather than forget the VMM. A fence whose forced stop the engine's own bound ends now reports `forced stop timed out`, as when the fence's bound ends it ([#482], [#459], [ADR 0074]).
- The engine's `start` and `stop` took no bound from their caller, so a stateful start under an `expiring` lease could not be held to the 3 s node-agent-protocol section 6.4 sets, and a self-fence, whose forced stop gets 0.3 s under such a lease, could only stop waiting for a slow stop. The engine now takes the caller's bound on every start and on both stop modes. A start that is not running by its bound returns `Timeout` and stops by force what it started, so it never leaves a VM it booted running. A forced stop returns `Timeout` at its bound and still finishes the kill, sending `SIGKILL` by half of a short bound. A graceful stop asks the guest until its timeout, then stops it by force, and returns within both bounds. The node agent passes the fence its `T_grace` and `T_force`, and 3 s to a stateful start under an `expiring` lease. Every other start gets 60 s, and every other forced stop 90 s, both longer than any that works today, so nothing else changes behavior ([#455], [#434], [ADR 0242], [ADR 0243]).
- The typed `node.fenced` and `node.fence_failed` data in `quoro-proto` lacked the `fencing_tokens` and `vm_ids` the node agent sends since [#445], and could not be serialized or parsed. Both now carry them and read and write the shape of `events.schema.json`; an event from a node before M5b still parses ([#458], [#456]).
- A forced stop of a VM whose Cloud Hypervisor process hung sent `SIGKILL` only after about 5 s, so a self-fence, whose forced stop gets 0.3 s under an `expiring` lease, could not kill a hung VMM in time. A fence that gave up on the stop also left the VM `stopping` and never killed it. A forced stop now kills a VMM that does not answer at once, and one that answers but does not exit within 150 ms, so `SIGKILL` goes out within 250 ms. It finishes the kill on its own task even when its caller stops waiting. A graceful stop of the same VM hands over to it at once instead of holding the VM until its own timeout, and a later stop waits for the one in progress ([#447], [#434], [ADR 0074]).
- A node refused a fence acknowledgement that arrived while a fence of one of the listed leases was still running, so it stayed failed until its next session. Section 5.17 says it answers `ok`. The node now clears the failures recorded before the acknowledgement and answers `ok`, naming any fence still running in `detail`. A failure that running fence records afterwards is not covered: the node is failed again, the primary lists the lease again, and only a new acknowledgement clears it ([#440], [#430], [ADR 0238]).
- While a node fenced a lease, its reconciler could stop the same VM itself, with its own 10 s graceful stop. The engine runs one operation per VM at a time, so the fence's stop waited behind it, timed out, and reported the fence failed: the node marked itself failed, and an operator had to acknowledge a fence that had in fact stopped the VM. For an `expiring` lease, the VM could also outlive its deadline. The reconciler now leaves a VM to its lease's fence until the fence has stopped it: it begins no stop of its own, and it gives up a stop already under way as soon as the fence is triggered. The lease service backs this up: when a lease stops being held, the same step that changes its state marks the fence as under way. A revoke of an `expiring` lease now begins its fence before its state is written, as an expiry already does ([#439], [#429], [ADR 0075]).
- While a node fenced a lease for a revoke, its session sent and read nothing else until the fence finished, heartbeats included. A `local` lease's fence can take up to 15 s (a 10 s graceful stop, then a 5 s forced one), which reaches the primary's 15 s session timeout, so the primary could mark the node `disconnected` in the middle of a fence it had asked for. The session now keeps sending heartbeats, answers `ping`, and applies lease grants for other leases while the fence runs; every other message waits and is processed in the order it arrived once the revoke is answered ([#428], [#427], [ADR 0222]).
- After a restore moved an app to another node, the old node recreated the app's VM, stopped and without its volume, and kept it with its Cloud Hypervisor process until the node agent restarted. The old node now deletes the VM as soon as the restore is accepted, and keeps only the detached volume's file ([#361]).
- After a primary restart, a node could take up to about 25 s to reconnect: when its first redial found the primary's listener still down, it tried every address the primary advertised, each with a 10 s connect timeout, before it dialed the primary's address again. A node now dials a primary that refuses the connection again for up to 2 s before it tries the other addresses, and gives each advertised address a 2 s connect timeout that grows with every failed attempt, so it reconnects within about a second of the restart. Stopping the node agent no longer waits for a dial in progress ([#368], [ADR 0139]).
- An edge reported a backend leaving or rejoining the rotation to the primary only with its next periodic status report, so the API and the panel could lag the edge by up to 30 s. The edge now sends a status report as soon as its backend list changes. A backend's `last_error` now names the backend and the root cause, in the same words whether the proxy or a health probe saw the failure, instead of `client error (Connect)` or `client error (SendRequest)` ([#369], [ADR 0143]).
- While a node was disconnected, the app's Instances list and the VM API kept showing its instances as `running`, the status the node last reported. The API now shows them as `unknown` until the node is connected again, and the panel says why: `unknown (node disconnected)`. Nothing is written for it: the primary keeps the last report, so a disconnect or a primary restart emits no event and changes no deployment ([#377]).
- A node reported a newly applied revision to the primary only with its next periodic status report, unless the revision also changed a VM or a route, so `applied_rev` in the API could lag by up to 30 s, on an edge above all. The node now sends a status report about 250 ms after it applies a revision ([#379]).
- A terminal command that finished before the client's WebSocket attached could not be read: the upgrade answered `401`, as if the ticket were bad, and the command's output and exit code were lost. A command with no output that exited within about a second was refused with `409`. The session now keeps the output and the exit until its ticket expires, so the client receives them, then `exit` and `closed`, and the audit record shows the session as connected ([#381], [ADR 0186]).
- A node agent that died in the middle of a self-fence came back with the lease revoked but did not stop its VMs again, and the VMs outlive the agent, so a VM could keep running without its lease. The agent now records a fence, together with the lease's state, only once its stop has finished, answers the revoke `ok` only once that record is written, and fences again at start any revoked or expired lease without a record. A fence also stops the VMs the latest desired state no longer names, so a VM dropped from it just before the revoke is not missed. Fences of different leases now run at the same time instead of one after another, the agent keeps taking messages while one runs, and a stateful VM no longer starts while a fence of its lease is under way ([#385], [ADR 0075], [ADR 0019]).
- After a restore was accepted, the old node could still receive a desired state that named the moved VM after its lease had been revoked, when that snapshot had been built just before the restore. A snapshot built before a lease revoke is now dropped and built again, so nothing the revoke took away reaches the node after it. Deleting a volume had the same race ([#388]).
- The panel offered `app:terminal`, `backup:manage` and `backup:restore` in the agent grant and webhook forms, and the API then refused the grant. Its human-only and destructive scope lists now match the permission model, and a test reads both lists from the contract ([#397]).
- The panel's webhook dialog did not offer the `build`, `backup`, `restore`, `volume` and `domain` events, so they could only be subscribed to through the API. The dialog now offers every event type of the contract, grouped by subject ([#398]).
- Re-running the installer to upgrade a set-up primary printed `warning: could not read a setup token` and the first-run steps again, and a node or an edge printed its first-run text. The installer now reads the version it replaces and says `upgraded from 0.1.1 to 0.2.0`. On a primary whose cluster is set up, it skips the setup token and the first-run steps and names the next step, upgrading the nodes and edges. A re-run without `QUORO_ROLE` on a node or an edge installed a second control plane next to the agent; the installer now refuses it and names the role to pass. The installer README documents the `edge` role, the `QUORO_JOIN_*` variables for an edge, and how to upgrade ([#401]).
- After a primary restart, the desired state could name a new digest for an app instance that was already running: the primary resolved the image tag again with an empty cache, and if the tag had moved, it asked the node for a digest no instance runs. The node refused the change, as a VM's digest is fixed when it is created, and logged the same warning on every pass. An instance now keeps the digest its deployment recorded when it was created; only a new deployment resolves the tag again. The node logs the refusal once per VM and digest ([#403]).
- A terminal opened on a VM that was still booting was refused with "the VM's init does not accept exec sessions; restart the VM", although the VM only needed a few more seconds: its init accepts terminals once it has mounted the volumes and set up the network. The message now says the VM may still be starting, and that only a VM which has been running for a while needs a restart. The engine's KVM test suite now waits for the guest before its first command, and its teardown removes both of the bridge's firewall tables instead of only one ([#418]).
- Deleting an app deleted its volume records at once, so the node was never told and the volume files stayed on its disk until an operator removed them. Every volume of the deleted app now stays `deleting`, readable with `getVolume`, until its node removes the file and reports it, and its node is told even when it keeps only a detached volume. The holder of the app's lease now also receives the `lease_revoke` with reason `deleted` that deleting the app was meant to send ([#420], [ADR 0165]).
- Every domain stayed `pending` in the API and the panel, even while its hostname was served: nothing computed a domain's serving status. The primary now recomputes it whenever an app's instances, its replicas, a domain, a tunnel mapping or the edge change, and at least every 30 s. A domain is `serving` when a machine serves its hostname, `unserved` with the reason in `last_error` when its app has an instance meant to run but no machine can serve it (for example a `tunnel` hostname of a one-replica app whose node has no tunnel), and `pending` while its app runs no instance. Becoming `unserved` emits `domain.unserved`, and being served again emits `domain.served` with the time it became `unserved`, even when the app was stopped in between; a `tunnel` domain no tunnel serves is no longer reported as `certificate.failed`. The app's Domains card shows the serving status and the reason ([#422], [ADR 0167]).

### Security

- rmcp, the MCP SDK, moves to 3.9 (RUSTSEC-2026-0462). Before 3.9.0 its Streamable HTTP clients read a server's response body with no size limit, so a hostile MCP server could exhaust the client's memory. Quoro uses only rmcp's server side and was not exposed, but the dependency check fails on 3.8 ([#620], [#618]).
- The dependency check ignores RUSTSEC-2026-0459 for now. The SQLite that sqlx bundles, before 3.54, can return uninitialised memory when it opens a database together with a crafted `-wal` file. Quoro opens only the SQLite files it writes in its own data directory, a restore removes stale `-wal` and `-shm` files before it opens the database, and the image inventory reads `rpmdb.sqlite` with its own reader, not with SQLite. No sqlx release takes the fixed SQLite yet; the ignore goes once one does ([#619]) ([#620], [#618]).

### Known issues

- A node can report a disk capacity of 0, as a single-machine test cluster did: `GET /api/v1/nodes` gives `capacity.disk_gb` 0, and the Nodes page says the node reports no disk capacity instead of drawing its disk meter ([#636]).
- `DELETE /api/v1/vms/{vm_id}` removes the VM's record at once, so `getVm` answers `not_found` straight away. The contract describes the VM staying, with `observed_status` moving to `deleted`, so a client cannot see when the node has removed the VM and its disks ([#599]).
- `deleteProject` is in the contract, but the primary does not serve it: `DELETE /api/v1/projects/{project_id}` answers `405`, and `quoro project delete` says that nothing was deleted ([#515]).
- Personal API tokens always read "never used": nothing writes their `last_used_at` ([#504]).
- On a node that snapshots volumes by pausing the VM (`pause_copy`), a VM can stay paused while it is reported `running`. This happens when the node agent dies while it stops a VM that a backup paused, to restart that VM: after the agent restarts, the engine does not resume a VM whose stop was requested ([#539]).
- A VM created through `POST /api/v1/vms` with an image tag resolves the tag again after a primary restart. If the tag has moved, the desired state names a digest the VM does not run; the node refuses the change, logs it once and keeps the VM as it was. A VM created with a digest reference (`@sha256:`) is not affected, and neither are app instances ([#404]).

### Upgrading from v0.2.0

- Upgrade the primary first, then every node and edge to the same version: re-run the installer with the version and, on a node or an edge, its role (`QUORO_ROLE=node` or `QUORO_ROLE=edge`). An enrolled host needs no join token. The installer now reports the upgrade (`upgraded from 0.2.0 to 0.3.0`), skips the first-run steps on a primary that is set up, and refuses to install a control plane on an enrolled node or edge that is upgraded without its role ([#401]). Health-check restarts, the guest flush before a snapshot and the grace window for a `tunnel` hostname that moves run in the node agent, so they take effect on a machine only once its agent runs v0.3.0.
- The control-plane database moves from schema version 9 to 14 (migrations 0009 to 0013). When a backup repository is configured, the new primary backs the database up at its first start, before it migrates and before it listens ([ADR 0157]). If that backup fails, the primary migrates nothing and exits with the reason. A later start tries again, and `quoro serve --skip-upgrade-backup`, run once, migrates without the backup and records the skip in the audit log. Without a repository, the primary logs that it migrates without a backup. A v0.2.0 binary does not open the migrated database.
- The pre-upgrade backup makes the primary's restart longer, and the nodes are without a session until it ends. On the test lab the API was down for about 2.6 s, and a node with several primary addresses took about 8 s to reconnect; nothing failed ([#587]).
- Every app has a health check (`/` on the app port by default), and a node now restarts an instance that fails it `failures` times in a row outside its start period (30 s by default), with the crash backoff. An app created before this release has no `restart` setting, which means true, so this applies to it too. To keep v0.2.0's report-only behaviour for an app, set `health_check.restart` to `false` with `updateApp` ([#511], [ADR 0184]).
- A running VM gets the new `quoro-init`, which flushes a volume's filesystem before each snapshot, only at its next start. Until then its snapshots are crash-consistent, as in v0.2.0 ([#635], [ADR 0282]).
- On a node that snapshots volumes by pausing the VM (`pause_copy`), avoid upgrading the node agent while a backup copies a volume. A VM that the v0.2.0 engine left paused is not resumed after the upgrade: stop it and start it again ([#523]).
- Every two machines with the `node` or `witness` role now also become direct WireGuard peers on the mesh's UDP port (51820 unless the operator changed it), not only peers of the edge ([#671], [ADR 0266]). Nothing in this release sends traffic over those peers yet: they are for M5b's votes and warm replication. Where a firewall sits between nodes, open that UDP port between them before those features arrive.
- After the upgrade, each node receives the primary's whole change log once, from its first entry, and keeps it in its own database, which grows by about the size of the primary's log. Secrets in the log (environment variable values, webhook and provider secrets) stay encrypted with the cluster key, which nodes do not hold ([#668], [#697]).
- A node that marked itself failed under v0.2.0, because a self-fence could not confirm that a VM stopped, stays failed after the upgrade until a human acknowledges it. Its agent reports the stored failure again, the primary lists it in the node's `fence_failure` (`GET /api/v1/nodes/{node_id}`), and a human calls `POST /api/v1/nodes/{node_id}/fence-ack` with the listed lease ids after checking out of band that the VMs are stopped ([#423], [#544]).

## [v0.2.0] - 2026-11-05

Milestone M5a: stateless replicas behind an edge, local volumes, cold backups and vulnerability tracking. The milestone is complete: its demo ran on the lab and was approved on 2026-11-05. Still an experimental preview, not for production ([ADR 0137]).

### Storage

- **Local volumes.** An app can have a persistent volume on its node: `POST /apps/{app_id}/volumes` with a size and a mount path. The guest mounts it at boot, and the volume is attached again to the new VM on every redeploy. The app's node holds a `local` lease for it, and an agent needs a human's approval to delete a volume ([#251], [#259], [ADR 0145], [ADR 0019]).
- **Snapshots without pausing the app.** Volume snapshots use reflink when the node's data directory supports it. When it does not (ext4, for example), the node keeps its volumes in a loop-mounted XFS pool that can reflink, so a snapshot clones the file instead of pausing the VM ([#251], [#272], [ADR 0146], [ADR 0156]).
- **Chunk engine.** A new `quoro-backup` crate splits data into content-defined chunks, then compresses and encrypts every chunk on the client before upload. A recovery key protects the repository key ([#252], [ADR 0147]). It is paired with a new S3-compatible object-store client that writes without overwriting and probes a bucket's object lock ([#253]).
- **Cold backups and restore.** Apps with the `cold` policy back up their volume to an S3-compatible bucket on a schedule or on demand, and a backup can be restored onto another node. The recovery key is shown once and can be rotated ([#273], [ADR 0147]).
- **Control-plane backups.** The primary backs up its database with `VACUUM INTO` every 6 hours by default, through the same chunk engine. The new binary takes another backup before it runs any schema migration, and keeps the newest three of those outside the scheduled retention. `quoro restore` restores a backup offline, onto the same host or a new one ([#274], [ADR 0148], [ADR 0157], [ADR 0158]).
- **Off-site audit copy.** The primary copies the audit log to an S3-compatible bucket in segments that are never overwritten. A daily probe checks how strongly the bucket locks objects and records the result, and audit verification now detects a local log whose tail was cut, or that differs from the copy ([#275], [ADR 0149]).
- **Panel.** The app screen gains a storage section: its volumes, its backups with "back up now" and restore, and the backup schedule. The HA policy selector shows what `cold` costs next to the current policy. The audit screen shows the off-site copy, its lock strength and its last error ([#276], [ADR 0020]).
- Contracts for this work: the storage contract shipped in v0.1.1 ([#226]); later amendments covered the XFS volume pool ([#255]), the pre-upgrade backup ([#270]) and the audit export after a restore ([#298]).

### Replicas, mesh and edge

- **A guest subnet per node.** Every node gets its own /24 guest subnet from the primary. Running VMs keep their address and move to the new subnet on their next deploy. Upgrade the nodes together with the primary: an older node agent refuses the new subnet ([#256], [ADR 0144]).
- **Mesh.** The edge and the nodes are joined by a kernel WireGuard star with the edge as the hub, configured by the node agent over netlink. Each machine's private key never leaves it, and only the edge can reach a guest over the mesh ([#260], [ADR 0144]).
- **Replicas.** A stateless image app can run several replicas, at most one per node. A deploy rolls out one new instance per node and checks each instance's health before it retires the old ones; a failed rollout leaves the old instances serving. Changing the replica count needs no new deploy, and an app with only some of its instances up is reported `degraded` ([#261], [ADR 0142]).
- **Edge role.** `quoro join --role edge` enrolls a machine that runs no VMs and needs no KVM. The edge routes every replicated app round robin over its healthy replicas and runs its own health checks, so it takes a failed replica out of rotation and puts it back once it recovers. It keeps serving its last known routes while the primary is unreachable, and reports backend health to the primary ([#262], [#242], [ADR 0143]).
- **Panel.** The app screen shows the replica count, the node each instance runs on, and, behind an edge, each backend's rotation state and last error ([#263]).
- The contract for replicas, the edge and the mesh shipped in v0.1.1 ([#227]).

### Vulnerability tracking

- **Image inventory.** Every image a node prepares gets a package inventory, which the node sends to the primary. The inventory reads Debian, Alpine and RPM package databases, npm lockfiles, Python package metadata, Go build info and `cargo auditable` data, all inside the image root and without running anything from the image ([#300], [ADR 0150], [ADR 0151]).
- **Local OSV mirror.** The primary keeps its own copy of the OSV data for the ecosystems its images use, plus CISA's Known Exploited Vulnerabilities (KEV) catalog. It checks for updates hourly, and `quoro vuln import` loads the data offline ([#305], [ADR 0150]).
- **Findings and the `app.vulnerable` incident.** The primary matches each inventory against that data with each ecosystem's own version ordering and records the findings. A new finding that is in KEV, or scores 9.0 or more in CVSS, raises `app.vulnerable`. That opens an incident, which can wake an agent. The API serves the findings per app and as a cluster summary ([#307], [ADR 0150], [ADR 0160]).
- **SBOM and Quoro's own components.** The release build writes a CycloneDX SBOM that the release workflow attests, and the same component list is compiled into the binary. The primary checks Quoro's own crates, the guest kernel, Cloud Hypervisor, cloudflared, BuildKit and every node's host kernel against the same data. Host kernels stay the operator's: Quoro reports them and never upgrades them ([#309], [ADR 0138], [ADR 0151], [ADR 0161]).
- **Panel.** The app page has a "Vulnerabilities" section: what was checked, the age of the data, counts by severity, and the open findings with filters. The nodes page shows a cluster summary for the Quoro release, the guest kernel and each host kernel ([#310], [ADR 0138]).
- **Rebuild with refreshed base.** A Git app can be rebuilt with every base image pulled again, from the vulnerability section or next to "Build now" (`startBuild` with `refresh_base: true`). An automatic rebuild on a critical finding is deferred to M5b ([#294], [#310], [ADR 0155]).
- **Images cached before M5a.** A node now inventories, once and in the background, the images it cached before M5a, reading their cached root disk. No redeploy and no network access is needed ([#318], [#320], [ADR 0163]).
- **Linux kernel ranges.** Kernel findings are read per stable series, so a fully patched kernel on an older series is no longer flagged ([#314], [ADR 0162]). Ranges whose fix is below the version that introduced the bug are now ignored ([#323]).
- The contract for vulnerability tracking shipped in v0.1.1 ([#237]); the decisions taken while building it are ADRs 0160 to 0163 ([#319]).

### Fixed

- The edge could lose its WireGuard sessions with the nodes on every mesh refresh, which took replicas out of rotation for up to 25 seconds. Peers are now updated in place ([#285]).
- A VM created before its node's subnet changed could not start again after a host reboot. It now starts on the bridge it was created with ([#281]).
- A browser that opened a terminal just as its session ended got a reset connection. It now receives the real reason the session closed ([#278]).
- A node reported 0 GB of free disk, so the primary refused to create volumes on it ([#272]).
- After `quoro restore`, the restored primary showed the backup it came from as still running, which blocked scheduled backups for 24 hours. Interrupted control-plane backups are now resolved from their seals at start ([#301], [#302]).
- After `quoro restore` onto another host, the primary role now moves to that host's node ([#299], [#304]).
- A build's log stream could end without the build's last line ([#315]).
- A second process writing the database while the server ran (for example `quoro vuln import`) could make a write fail with "database is locked" ([#316]).
- A repository's first backup could start the garbage-collection sweep, which then refused new backups while it ran. The sweep now runs only after a pruning ([#317]).
- A node session that had already been replaced could, while closing, mark its live node as disconnected. Only the node's current session now records a disconnect ([#325]).
- Writes to the vulnerability cache could queue for many seconds while each one held a pooled connection, which stalled node sessions until they timed out. The cache now takes one writer at a time, and queued writers no longer hold connections ([#328]).
- When a replica died without closing its connections, a request the edge had already sent to it over a pooled connection waited for the full 60 second response timeout. The edge now cancels the requests still waiting on a replica that leaves the rotation, and drops its pooled connections. A `GET` or `HEAD` that has not answered yet is retried once on another replica, and any other request answers `502` at once ([#334]).
- A `GET` sent to a replica's pooled connection right after the replica died still got a `502` after about 20 seconds when the replica's host reported it unreachable. It is now retried once on another replica, and the replica leaves the rotation at once. A client that reset its own upload could also take a healthy replica out of rotation; it no longer does ([#338]).
- A machine with only the edge role always reported `applied_rev` 0 in `GET /api/v1/nodes`. It now reports the newest desired state it has applied ([#341]).
- A new `tunnel` domain, or a hostname that moved between a node and the edge when an app's replica count crossed 1, could wait up to 60 seconds for its tunnel route when the machine had no live session. The primary now publishes those changes at once. After such a move, the old tunnel could also delete the CNAME the new tunnel had just pointed at itself, which left the hostname without DNS. A tunnel now deletes a CNAME only while that CNAME still points at it ([#343]).
- Scaling an app with `tunnel` domains down to one replica could keep the instance on a node without a tunnel, and the hostnames stopped answering with no sign of why. A scale-down now keeps the instances on nodes with a tunnel first. When no remaining instance can serve the app's `tunnel` domains, each one gets a `certificate.failed` event with `tls_mode` `tunnel` ([#347]).
- When a `tunnel` hostname moved between a node's tunnel and the edge's, the tunnel that lost it deleted its CNAME and the other tunnel created a new one. Cloudflare took longer to route the new record, and the hostname answered `404` for up to about a minute. The tunnel that gains the hostname now repoints the existing record, and the one that loses it leaves the record alone. The losing node still stops serving the hostname at once, so a short window of `404`s remains ([#348]).

Tests that failed intermittently on loaded CI runners were made deterministic ([#265], [#269], [#282], [#286], [#340]). A changelog and a milestone status table were added ([#329]). ### Known issues

- Changing the replica count of an app with `tunnel` domains across 1 moves its hostnames between a node's tunnel and the edge's. For up to about two minutes afterwards, part of the requests answer `404` while Cloudflare moves traffic to the new tunnel. The DNS record is kept; a grace window, in which the machine that lost the hostname keeps serving it, is planned for M5b ([#344]).
- While a node is disconnected, the app's instances list keeps showing that node's instance as `running`. The edge backends, the metrics and the nodes page show the outage ([#342]).
- The primary's API can take up to about 30 seconds to show that the edge took a backend out of rotation. The edge itself acts within seconds, so traffic is not affected ([#339]).
- `applied_rev` in `GET /api/v1/nodes` can lag the revision a machine has applied by up to about 30 seconds when the revision changes no VM and no route ([#346]).
- Web terminal: a command that ends before the client attaches its WebSocket loses its output, and the upgrade answers `401`. The command still runs. An interactive shell is not affected ([#240]).

### Upgrading from v0.1.1

- Upgrade the node agents together with the primary. An older node agent refuses the per-node guest subnet, and the primary treats a node agent older than M5a as one that cannot hold a volume ([ADR 0144]).
- Every node except the oldest gets its own guest subnet. Running VMs keep their address and move to the new subnet on their next redeploy.
- After its node agent starts, a node inventories the images it cached before this release, once and in the background. No redeploy is needed ([ADR 0163]).
- The installer now installs the optional `xfsprogs` package when `mkfs.xfs` is missing. Without it, a node whose data directory cannot reflink (ext4, for example) pauses the app to snapshot a volume ([ADR 0156]).
- From this release on, a new binary backs up the control-plane database before it applies a schema migration, when a backup repository is configured ([ADR 0157]). v0.2.0 applies no migration to a v0.1.1 database, so this upgrade takes no such backup.

## [v0.1.1] - 2026-11-04

Still an experimental preview, not for production ([ADR 0137]). This release carries the groundwork for M5a: the guest kernel, a primary that can change address, durable webhook delivery, and the M5a contracts.

### Added

- **Quoro's own guest kernel.** App and builder microVMs boot Linux 7.2.15, built by Quoro from upstream stable plus Cloud Hypervisor's guest patches and `ch_defconfig`. It fixes CVE-2026-98432 in the guest kernel. The kernel ships as its own signed release, `guest-kernel-7.2.15-q1`, which `packaging/kernel/reproduce-kernel.sh` reproduces bit for bit, and the installer pins it by sha256 ([#229], [#244], [ADR 0152]).
- **Nodes follow a primary whose address changes.** The primary advertises its addresses when a node connects, and a node that cannot reach its primary tries them with the same pinned certificate. `quoro node set-primary <url>` points a node at a new address by hand ([#215], [#222], [#223], [ADR 0139]).
- **Webhooks survive primary restarts.** Delivery is at-least-once, with the event id as the deduplication key; a restart no longer drops events that were committed but not yet sent ([#214], [#221], [ADR 0140]).
- The M5a plan and contracts: vulnerability tracking planned ([#213], [ADR 0138]), spike notes ([#217]), and the contracts for storage ([#226]), for replicas, the edge and the mesh ([#227]), and for vulnerability tracking ([#237]).

### Upgrading from v0.1.0

Running VMs keep the kernel they booted with. Redeploy each app to move it to the 7.2.15 kernel.

## [v0.1.0] - 2026-11-04

Quoro's first public preview, carrying milestones M3 and M4. **Experimental, not for production**; expect breaking changes before the first general release ([ADR 0064], [ADR 0137]).

### Added

- **Agents as their own identities.** A service layer shared by the API and MCP, with agents, agent keys and `atk_` access tokens, and panel screens to manage agents, their keys and their grants ([#106], [#107], [#136], [ADR 0106]).
- **Grants and approvals.** Every call is authorized against the caller's scoped, time-limited grants. Destructive agent actions wait for a human's just-in-time approval, which the panel's approvals queue handles ([#108], [#113], [#114]).
- **Audit log.** List and read audit records and verify the hash chain, from the API and the panel ([#108], [#115]).
- **MCP server.** `/mcp` serves the same operations as the API, with tools for approvals, events, incidents and the audit log, and `quoro mcp stdio` connects local MCP clients ([#117], [#120], [#121], [#138]).
- **Events, incidents and webhooks.** Signed webhooks deliver events and can wake an agent for an incident, with `data.wake` naming the agent and its grant. The panel lists deliveries, sends test deliveries and marks them as tests ([#109], [#116], [#134], [#152], [#153], [ADR 0103], [ADR 0104], [ADR 0111]).
- **Reference agent runner** in `examples/agent-runner`, with a built-in deterministic policy ([#118], [#135], [ADR 0049], [ADR 0102]).
- **User names everywhere.** Operators and viewers can resolve user ids to names ([#134], [#136], [ADR 0107]).
- **Git apps.** An app can be created from a public Git repository with a Dockerfile. Each build runs on the target node in an ephemeral BuildKit builder microVM, and the built image is deployed. The panel follows a build live, and a failed build shows its failing step and log ([#171], [#172], [#173], [#174], [ADR 0117], [ADR 0118], [ADR 0122], [ADR 0123], [ADR 0124], [ADR 0125]).
- **Metrics.** CPU and memory for every node and app, sampled by the node agent, served by the API and shown live in the panel ([#164], [#167], [#168], [ADR 0129]).
- **Web terminal and VM console.** Humans can open a terminal into an app; every session is audited and its transcript is hashed. Every VM also has a read-only serial console. Both are opened with single-use tickets and relayed through the node agent ([#177], [#178], [#179], [#180], [#181], [ADR 0113], [ADR 0114], [ADR 0115], [ADR 0116], [ADR 0126], [ADR 0127], [ADR 0128]).
- **Users.** Invite users with roles and manage them from the API and the panel, and let a signed-in user change their own password ([#165], [#166], [#201], [#205], [ADR 0135]).
- **Documentation site.** The docs are built as an mdBook site in CI and published to GitHub Pages on every release ([#132], [#200], [ADR 0109], [ADR 0130]).
- The M3 and M4 contracts and spike notes ([#133], [#155], [#156], [#160], [#163], [#202]), ADRs 0102 to 0136 ([#131], [#159], [#194]), and the M2 and M3 Definitions of Done marked as met ([#111], [#146]).

### Changed

- VMs created before this version have no vsock device and no socket-mode serial port. Their terminal and console show "Redeploy to enable": a restart is not enough, only a redeploy adds them ([#204], [ADR 0136]).
- CI now type-checks, tests and builds the panel and tests the agent runner ([#125]).

### Fixed

- Webhooks never delivered from the release binary, because no TLS crypto provider was installed ([#126]).
- `quoro mcp stdio` now negotiates the MCP protocol version with the client ([#142]).
- The agent runner sends its User-Agent when it checks a URL, reports the status it saw, and waits for the app's health check before it reports a recovery ([#143], [#144]).
- The engine accepts the host-side port in Cloud Hypervisor's hybrid vsock reply ([#185]).
- The installer installs `git` on hosts that run the node agent ([#186]).
- A node's allocated capacity is summed from its VMs when it is read, so it no longer drifts ([#188]).
- The transcript hash is recorded when the primary ends a terminal session ([#191]).
- A build waiting for capacity fetches its source once and logs the wait once ([#207]).
- Tests of the node session, webhooks and VMM start-up are deterministic, and the release build image retries apt ([#203], [#208]).

### Upgrading from v0.0.2

Redeploy each app that needs the terminal or the console; see "Changed" above.

## [v0.0.2] - 2026-11-03

Milestone M2: deploy an OCI image with a domain and TLS, through nodes that keep running when the control plane is gone.

### Added

- **Dial-out node agent.** Nodes enroll with the primary, dial out to it, receive a signed desired state and reconcile it locally ([#71]).
- **Privilege split.** The control plane runs unprivileged; only the node agent runs as root, as its own service ([#73], [ADR 0089], [ADR 0096]).
- **Providers.** An API for provider credentials, with secrets encrypted under the cluster data-encryption key ([#70], [ADR 0050]).
- **App VMs.** The node agent runs app VMs with console log capture, health checks and log streams ([#84]).
- **Apps, deployments and domains API,** with live logs over server-sent events ([#85]).
- **Panel.** A deploy screen, the app list and detail, and a live log view ([#86]).
- **Ingress.** An ingress interface with the embedded reverse proxy and a Cloudflare Tunnel backend. The primary manages one tunnel per node and the ACME DNS-01 challenges; nodes serve app routes through the tunnel connector or ACME, and the installer installs `cloudflared` ([#82], [#83], [#88], [#89], [ADR 0059], [ADR 0094]).
- **Certificate events** name the domain they are about ([#93], [ADR 0099]).
- Contract additions: isolation groups, guest DNS, log fields and node credentials ([#69]); per-node tunnel tokens and DNS-01 through the primary ([#80]); `disk_gb` of at least 1 for apps and `domain_id` on routes ([#92], [ADR 0098], [ADR 0099]). ADRs 0094 to 0099 ([#81], [#91]), and the M1 Definition of Done marked as met ([#60]).

## [v0.0.1] - 2026-11-03

Milestones M0 and M1: frozen contracts, then a one-command install with the engine lifecycle and a basic panel. Both v0.0.x builds came before the first public preview, v0.1.0.

### Added

- **The bases.** Governance files and agent rules, sourced research, the product requirements, the roadmap, the glossary, the architecture, the threat model and the M0 contracts with a contract checker ([#1], [#2], [#3], [#4], [#22]).
- **Engine contract.** The `Engine` trait with an in-memory fake engine, and the node lease state machine with self-fencing ([#13], [#14], [#21], [ADR 0019], [ADR 0071]). A failed fence is reported with `fence_failed` and acknowledged by a human through an endpoint ([#32]).
- **Boot spike.** A microVM boots from an OCI image ([#15]).
- **Cloud Hypervisor engine.** An OCI-to-ext4 image pipeline and Quoro's own guest init, the Cloud Hypervisor backend, and `quoro serve` running it ([#39], [#41], [#49], [ADR 0061]).
- **Control plane** with setup, sessions and the VM lifecycle API; a VM's `disk_gb` is at least 1 ([#37], [#43], [ADR 0083]).
- **Web panel,** embedded in the binary ([#40]).
- **One-command installer** ([#35]).
- **Signed, reproducible releases.** Release binaries are signed with keyless GitHub artifact attestations and built in a pinned container, so any host reproduces them; the release includes the panel and the engine runtime ([#34], [#50], [#57], [ADR 0027], [ADR 0081], [ADR 0090]).
- **CI.** A cargo workspace with a pinned toolchain, and `cargo-deny` enforcing the dependency license and advisory policy ([#12], [#33], [ADR 0080], [ADR 0086]).
- ADRs 0081 to 0090 ([#53], [#56]); smaller debug info in dev and test builds ([#46]).
